Дедупликация в OLTP vs OLAP системах

Специфика хранения и обработки данных в транзакционных (OLTP) и аналитических (OLAP) базах данных кардинально отличается. Это предопределяет различные архитектурные подходы к обеспечению уникальности записей и борьбе с дубликатами.

1. UNIQUE-индексы в OLTP (PostgreSQL)​

В классических строковых OLTP-системах (PostgreSQL, MySQL) гарантией отсутствия дубликатов выступают ограничения уникальности (UNIQUE CONSTRAINT) и уникальные B-Tree индексы.

CREATE TABLE users (
    id UUID PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL
);

Механика работы и ограничения в OLTP​

  • Синхронная проверка при вставке: При выполнении команды INSERT движок СУБД перед записью строки на диск обращается к B-Tree индексу в памяти, чтобы убедиться в отсутствии такого же ключа. При обнаружении дубликата транзакция немедленно прерывается с ошибкой уникальности (duplicate key value violates unique constraint).
  • Аппаратные затраты: Для поддержания UNIQUE-индекса СУБД должна постоянно обновлять дерево при каждой вставке или удалении. На высоких нагрузках (тысячи транзакций в секунду) это приводит к росту случайного чтения и записи, а также блокировкам страниц индекса в памяти.

2. Почему UNIQUE-индексы неприменимы в OLAP (ClickHouse)​

Аналитические колоночные СУБД (ClickHouse, Apache Doris) оптимизированы для приема массивов данных на высокой скорости (сотни тысяч или миллионы строк в секунду методом INSERT INTO ... VALUES (...)).

Причины отсутствия синхронных UNIQUE-ограничений в ClickHouse​

  1. Колоночное хранение: Данные одной таблицы физически разбиты по отдельным файлам для каждой колонки. Выполнение синхронного точечного поиска (Index Look-up) перед каждой вставкой полностью разрушает архитектурные преимущества колоночного формата и снижает скорость записи в сотни раз.
  2. Иммутабельность блоков: В ClickHouse данные записываются на диск неизменяемыми кусками (Part / Data Part). Изменение существующей записи по месту (In-place Update/Delete) физически невозможно без полной перезаписи всего файла куска.
  3. Отсутствие B-Tree индексов: Вместо точечных индексов ClickHouse использует разреженные индексы (Sparse Index) на основе PRIMARY KEY / ORDER BY, которые хранят метки не для каждой отдельной строки, а для каждой гранулы данных (по умолчанию 8192 строки). Проверить уникальность конкретной строки по разреженному индексу невозможно.

3. Асинхронная дедупликация через ReplacingMergeTree в ClickHouse​

Для обработки обновлений и удаления дубликатов ClickHouse предоставляет специализированное семейство движков таблиц — ReplacingMergeTree.

CREATE TABLE user_events (
    user_id UInt64,
    event_time DateTime,
    event_data String,
    version UInt64
) ENGINE = ReplacingMergeTree(version)
ORDER BY (user_id, event_time);

Принцип работы ReplacingMergeTree​

  • Разрешение дубликатов при слиянии: При вставке данных ClickHouse принимает любые дубликаты, если их ключ сортировки ORDER BY (user_id, event_time) совпадает. Вставка выполняется мгновенно.
  • Фоновое слияние (Merge): В фоновом режиме системный процесс ClickHouse периодически объединяет разрозненные куски данных (Parts) в более крупные. В процессе слияния для строк с абсолютно одинаковым ключом ORDER BY движок оставляет только одну запись:
    • Если указан параметр версионирования ReplacingMergeTree(version): сохраняется строка с максимальным значением колонки version.
    • Если параметр version не указан: сохраняется строка, записанная последней по времени физической вставки.

Особенность при чтении данных​

Поскольку процесс фонового слияния непредсказуем по времени, в таблице могут одновременно присутствовать неслитые дубликаты. Для получения гарантированно дедуплицированного результата на момент запроса используется модификатор FINAL (либо агрегации argMax):

-- Использование модификатора FINAL для принудительного схлопывания при чтении
SELECT * FROM user_events FINAL WHERE user_id = 42;

(Применяется с осторожностью на больших объемах данных, так как FINAL требует дополнительных затрат CPU на слияние потоков чтения в памяти).

4. Паттерн двухуровневой дедупликации (Redis + ReplacingMergeTree)​

В высоконагруженных потоковых системах (например, при чтении событий из Apache Kafka или RabbitMQ в ClickHouse) для обеспечения гарантии доставки Exactly-Once или At-Least-Once без перегрузки аналитической базы применяется гибридный двухуровневый паттерн:

[ Producer / Consumer ] 
       │
       ├── 1. Быстрая проверка (TTL Cache) ──> [ Redis (Set/Hash) ]
       │                                            │
       │ (Если события нет в Redis)                 │ (Если событие уже было - отброс)
       ▼                                            ▼
[ Вставка в ClickHouse ] <── 2. Фоновая дедупликация ── [ ReplacingMergeTree ]

Уровень 1: Оперативный кэш в Redis (In-Memory)​

  1. Каждое входящее событие имеет стабильный уникальный идентификатор (event_id).
  2. При обработке пачки сообщений воркер предварительно проверяет наличие event_id в Redis (через команды MGET или добавление SADD / SETNX с коротким TTL, например, на 24-48 часов).
  3. Если ключ найден в Redis, событие считается повторным (вследствие сетевого ретрая в брокере сообщений) и отсеивается на уровне воркера без обращения к ClickHouse.

Уровень 2: Долгосрочная дедупликация в ReplacingMergeTree​

  1. Оставшиеся после проверки в Redis уникальные события пачкой вставляются в таблицу ClickHouse типа ReplacingMergeTree.
  2. Если повторное сообщение пришло позже истечения TTL в Redis (например, при повторной заливке исторических данных через неделю), оно попадет в ClickHouse, но будет гарантированно схлопнуто фоновым механизмом Merge или отсеяно при аналитическом запросе через модификатор FINAL.

Итоговые преимущества гибридной схемы​

  • Снижение нагрузки на СУБД: До 99% сетевых дубликатов отсекаются в оперативной памяти Redis за микросекунды.
  • Гарантия целостности: Защита от долгосрочных повторов и коллизий на уровне колоночного хранилища.
