# Первичный ключ (Primary Key)

Первичный ключ (Primary Key) — это столбец или набор столбцов в таблице базы данных, который однозначно идентифицирует каждую запись (строку), обеспечивая её уникальность. Он должен содержать уникальные значения и не может быть пустым (`NULL`). Первичный ключ позволяет быстро находить записи, связывать таблицы через внешние ключи (Foreign Key) и поддерживать ссылочную целостность данных.

---

## 1. Синтаксис создания и изменения

Первичный ключ можно объявить при создании таблицы (`CREATE TABLE`) или добавить в существующую таблицу (`ALTER TABLE`).

### При создании таблицы
```sql
-- Вариант 1: Указание ограничений на уровне столбца
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL
);

-- Вариант 2: Указание ограничений на уровне таблицы (удобно при именовании индекса)
CREATE TABLE orders (
    order_id BIGINT,
    user_id BIGINT,
    order_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT pk_orders PRIMARY KEY (order_id)
);
```

### Добавление в существующую таблицу
```sql
ALTER TABLE products 
ADD CONSTRAINT pk_products PRIMARY KEY (product_id);
```

## 2. Автоинкремент (SERIAL, AUTO_INCREMENT, IDENTITY)

Для автоматической генерации последовательных числовых идентификаторов различные СУБД используют собственные типы данных или конструкции:

### PostgreSQL (`SERIAL` и `BIGSERIAL` / `GENERATED ALWAYS AS IDENTITY`)
В современных версиях PostgreSQL вместо устаревшего псевдотипа `SERIAL` рекомендуется использовать стандарт SQL `GENERATED ALWAYS AS IDENTITY`:

```sql
-- Современный стандарт SQL (Postgres 10+)
CREATE TABLE customers (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);

-- Классический подход (через SERIAL/последовательность)
CREATE TABLE legacy_customers (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);
```

### MySQL / MariaDB (`AUTO_INCREMENT`)
```sql
CREATE TABLE accounts (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    balance DECIMAL(15, 2) NOT NULL
);
```

## 3. Суррогатные vs Естественные ключи

При проектировании схемы БД выбор типа первичного ключа является одним из ключевых архитектурных решений.

### Естественный ключ (Natural Key)
Ключ, основанный на реальных бизнес-данных, обладающих природной уникальностью (например, номер паспорта, ИНН, ISBN книги, email, код валюты по ISO).
* **Преимущества:** Избавляет от необходимости создавать дополнительные столбцы; упрощает некоторые поисковые запросы.
* **Недостатки:** Бизнес-требования могут измениться (например, формат ИНН или email может поменяться, либо допустить дублирование), что потребует каскадного обновления всех связанных таблиц по внешним ключам.

### Суррогатный ключ (Surrogate Key)
Искусственно созданный идентификатор, не имеющий бизнес-смысла для пользователя (например, числовой `id` или `UUID`).
* **Преимущества:** Полный контроль над форматом и генерацией; неизменность во времени; компактность и высокая производительность индексов (при использовании последовательных целых чисел).
* **Недостатки:** Требует дополнительной проверки уникальности для реальных бизнес-полей (через ограничение `UNIQUE`).

## 4. Сравнение ID (Числовой автоинкремент) vs UUID

| Параметр | Числовой ID (`BIGINT`) | UUIDv4 (Случайный) | UUIDv7 / ULID (Сортируемый) |
| :--- | :--- | :--- | :--- |
| **Размер в памяти** | 8 байт | 16 байт | 16 байт |
| **Скорость B-Tree индекса** | Максимальная (последовательная вставка) | Низкая (случайный разброс, фрагментация страниц) | Высокая (монотонное возрастание по времени) |
| **Генерация на клиенте** | Невозможна (требует обращения к БД) | Возможна без координации с БД | Возможна без координации с БД |
| **Безопасность API** | Низкая (легко перебрать id: 1, 2, 3...) | Высокая (невозможно предсказать следующий) | Средняя (временная метка читаема, хвост случаен) |
| **Распределенные системы** | Требует координации или разделения диапазонов | Идеально подходит | Идеально подходит |

## 5. Составной ключ (Composite Key)

Составной первичный ключ состоит из двух и более столбцов. Ни один из столбцов по отдельности не гарантирует уникальность строки, но их комбинация обязана быть уникальной.

Часто применяется в таблицах связей при реализации отношения «Многие-ко-Многим» (Many-to-Many):

```sql
CREATE TABLE user_roles (
    user_id BIGINT REFERENCES users(id) ON DELETE CASCADE,
    role_id INT REFERENCES roles(id) ON DELETE CASCADE,
    assigned_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT pk_user_roles PRIMARY KEY (user_id, role_id)
);
```

### Правило порядка колонок в составном ключе
Порядок колонок при объявлении составного ключа критически важен для производительности поисковых запросов (правило левого префикса). Ключ `PRIMARY KEY (user_id, role_id)` позволит быстро искать записи:
* По `user_id` и `role_id` одновременно.
* Только по `user_id` (левая колонка).
Однако поиск **только** по `role_id` (правая колонка) не сможет эффективно использовать этот индекс и потребует полного сканирования индекса или таблицы.
