Архитектура Ingestion Pipeline: RabbitMQ + ClickHouse

При проектировании систем сбора метрик, логов, событий аналитики или трейсинга (Ingestion Service / Collector) встает критическая задача: как принимать десятки и сотни тысяч запросов в секунду и надежно сохранять их в аналитическую базу данных (ClickHouse) без потерь, задержек и падений серверов.

1. Почему прямая запись в ClickHouse убивает базу?​

ClickHouse — это колоночная аналитическая база данных (OLAP). Она спроектирована для того, чтобы мгновенно (за миллисекунды) агрегировать миллиарды строк по фильтрам и группировкам. Но за эту невероятную скорость чтения приходится платить сложностью записи.

Что происходит при поштучной записи (INSERT INTO events VALUES (...))?​

Когда ваш Go-сервис (или PHP-скрипт) отправляет в ClickHouse одиночные строки по мере их поступления, для каждой отдельной строки запускается тяжелейший конвейер:

  1. Парсинг и валидация: База разбирает SQL-запрос или HTTP-payload и проверяет типы данных по схеме таблицы.
  2. Сортировка: ClickHouse всегда сортирует данные по ключу (ORDER BY / PRIMARY KEY), чтобы обеспечить эффективный бинарный поиск и сжатие по гранулам.
  3. Создание куска (Data Part): Движки семейства MergeTree не дописывают строки в существующий файл. Для каждой вставки ClickHouse создает на жестком диске новую директорию (Part). Внутри этой директории создается:
    • Отдельный файл со сжатыми данными для каждой колонки (если в таблице 50 колонок — создается ~50 отдельных файлов!).
    • Файлы с засечками (marks) для каждой колонки.
    • Файл с первичным индексом (primary.idx).
    • Файл метаданных (checksums.txt).
  4. Фоновые слияния (Background Merges): Специальные фоновые потоки ClickHouse постоянно сканируют диск и склеивают сотни крошечных кусков (parts) в большие, пересортировывая данные и перезаписывая их на диск.

[!CAUTION] Явление Write Amplification (Усиление записи): При записи по 1 строке диск совершает гигантский объем паразитной работы. 1000 отдельных инсертов в секунду создадут на диске 1000 директорий и десятки тысяч файлов за одну секунду. Диск мгновенно захлебнется от мелких операций ввода-вывода (IOPS), фоновые потоки слияния перестанут успевать склеивать куски, и ClickHouse выбросит фатальную ошибку: DB::Exception: Too many parts in all data parts in table.

Аналогия из мира PHP и классического веб-разработки​

Представьте, что ClickHouse — это сложный метод CIBlockElement::Add() в Битриксе, который при добавлении каждого элемента дергает десятки связанных таблиц, пересчитывает фасетные индексы, сбрасывает кеш компонентов и шлет почтовые события. Если 1000 пользователей одновременно вызовут этот метод, база MySQL и PHP-FPM зависнут. Поэтому тяжелые операции всегда выносят в фоновые агенты или очереди. В мире распределенных систем и Big Data эту роль выполняет брокер сообщений.

2. Как пишет RabbitMQ (Легкая кавалерия)​

В отличие от ClickHouse, брокер сообщений (RabbitMQ, Apache Kafka) устроен максимально просто с точки зрения хранения. Для брокера ваше сообщение — это просто «тупой» массив байтов (JSON, бинарный Protobuf или MessagePack).

Почему RabbitMQ выдерживает огромный поток?​

  1. Никакого парсинга и индексов: RabbitMQ не разбирает содержимое сообщения, не строит по нему B-Tree индексы и не валидирует типы колонок.
  2. Append-Only Log (Журнал только для добавления): Вместо создания отдельных файлов под каждую запись, брокер берет поток байт и последовательно дописывает (Sequential I/O) его в конец одного большого файла журнала на диске.
  3. Кеширование ОС (Page Cache): Последовательная запись — это самая быстрая физическая операция для жестких дисков (даже старые HDD выдают 100–200 МБ/с при последовательной записи, а NVMe SSD — гигабайты в секунду). Операционная система идеально оптимизирует и кеширует такие операции.
[Ingestion Service] ──(10 000 RPS)──> [ RabbitMQ ] ──(Append-Only Log)──> [ Быстрый Sequential I/O ]

Там, где ClickHouse упадет от 1 000 одиночных инсертов в секунду, один средний сервер RabbitMQ легко принимает 30 000 — 50 000 сообщений в секунду (а Kafka — сотни тысяч).

3. Три главные проблемы, которые решает брокер​

Внедрение RabbitMQ между сервисом приема трафика (Ingestion Service) и базой данных (ClickHouse) решает сразу три фундаментальные архитектурные задачи:

1. Агрегация батчей (Надежность против Памяти)​

Чтобы ClickHouse работал быстро, данные в него нужно вставлять пачками (батчами по 10 000 — 100 000 строк за один запрос INSERT).

  • Без брокера: Ingestion Service вынужден копить события прямо в своей оперативной памяти ([]Event), ожидая, пока наберется батч. Если сервер упадет (ошибка в коде, OOM Killer, перезагрузка по SIGKILL), все накопленные в памяти тысячи событий бесследно исчезнут.
  • С брокером: Ingestion Service мгновенно отправляет каждое событие в RabbitMQ (где оно сохраняется на диск в Durable очереди) и сразу отвечает клиенту HTTP 200 OK. Отдельный воркер-потребитель (Consumer) спокойно вычитывает сообщения из брокера, копит батч в памяти и отправляет в ClickHouse. Если Consumer упадет с батчем в памяти — не страшно: он еще не отправил ACK брокеру, поэтому после перезапуска RabbitMQ отдаст эти сообщения снова. Потери данных = 0.

2. Сглаживание пиковых нагрузок (Backpressure / Buffering)​

Представьте резкий скачок трафика в 100 раз (распродажа, рекламная пуш-рассылка или DDoS-атака).

  • Без брокера: База данных начинает тормозить, запросы копятся в пуле подключений, Ingestion Service исчерпывает лимит горутин/сокет-дескрипторов и начинает отдавать клиентам HTTP 500. Происходит каскадный сбой всей системы.
  • С брокером: RabbitMQ принимает на себя весь удар. Во время пика очередь сообщений просто начинает временно расти на диске брокера. Ingestion Service продолжает быстро и стабильно отдавать 200 OK. А Consumer забирает данные из очереди ровно с той максимальной скоростью, которую способен переварить ClickHouse без перегрузки.

3. Отказоустойчивость при падении БД (Fault Tolerance)​

Любая БД периодически требует обслуживания: перезагрузка, обновление версии, миграции схемы или кратковременный сбой сети.

  • Без брокера: Пока ClickHouse недоступен, сервис сбора логов вынужден отбрасывать трафик или забивать свою оперативную память ретраями, пока сервер не упадет по OOM.
  • С брокером: Если ClickHouse лежит, Consumer просто не может выполнить INSERT. Он логирует ошибку и не шлет ACK брокеру. Ingestion Service даже не подозревает о проблемах с БД и продолжает принимать трафик от пользователей. Когда ClickHouse поднимется (даже через 2 часа), Consumer автоматически продолжит работу и разгребет накопленную очередь.

4. Экстремальные нагрузки и TCP Backpressure​

Что произойдет, если нагрузка вырастет настолько сильно (например, 100 000+ запросов в секунду), что даже RabbitMQ перестанет успевать физически сбрасывать сообщения на диск?

В RabbitMQ есть встроенный механизм защиты от перегрузки через TCP Backpressure (Обратное давление) и Publisher Confirms:

  1. Когда диск или память RabbitMQ перегружаются, брокер перестает отправлять подтверждения (ACK / Publisher Confirm) издателю.
  2. В Go-коде Ingestion Service вызов channel.PublishWithContext() (или внутренний канал отправки) блокируется, ожидая подтверждения.
  3. Буферы горутин заполняются, и Ingestion Service начинает контролируемо отклонять новые входящие HTTP-запросы от клиентов, отдавая статус HTTP 429 Too Many Requests или HTTP 503 Service Unavailable.

[!TIP] Это правильное и здоровое поведение распределенной системы. Лучше честно и быстро ответить части клиентов 429 Too Many Requests («мы временно перегружены»), чем позволить базе данных или брокеру упасть с концами по OOM, утащив за собой весь продакшен. Брокер выступает предохранителем, защищающим ядро системы.

5. Реализация Consumer на Go (Паттерн Batch + Ticker)​

В продакшен-архитектуре на Go Consumer должен сбрасывать батч в ClickHouse при выполнении любого из двух условий:

  1. Набрался полный батч (например, 10 000 сообщений) — для максимальной пропускной способности.
  2. Прошло фиксированное время (например, 3 секунды по time.Ticker) — чтобы данные не лежали в памяти слишком долго при низком трафике (обеспечение низкого latency).

Пример надежного воркера с Graceful Shutdown:​

package main

import (
	"context"
	"fmt"
	"log"
	"sync"
	"time"

	amqp "github.com/rabbitmq/amqp091-go"
)

type Event struct {
	ID        string
	Payload   string
	Timestamp time.Time
}

type ClickHouseConsumer struct {
	batchSize   int
	flushPeriod time.Duration
	ch          *amqp.Channel
	db          ClickHouseClient // Интерфейс к вашему ClickHouse драйверу
}

func (c *ClickHouseConsumer) Start(ctx context.Context, wg *sync.WaitGroup, deliveries <-chan amqp.Delivery) {
	defer wg.Done()

	batch := make([]Event, 0, c.batchSize)
	pendingDeliveries := make([]amqp.Delivery, 0, c.batchSize)

	// Таймер для сброса по времени (даже если батч не полный)
	ticker := time.NewTicker(c.flushPeriod)
	defer ticker.Stop()

	flush := func() {
		if len(batch) == 0 {
			return
		}

		// 1. Сохраняем батч в ClickHouse одним запросом INSERT
		err := c.db.SaveBatch(ctx, batch)
		if err != nil {
			log.Printf("[ERROR] Ошибка записи батча в ClickHouse: %v. Повтор при следующем цикле", err)
			// Если SaveBatch упал, мы НЕ шлем ACK! При перезапуске RabbitMQ вернет сообщения.
			return
		}

		// 2. Если запись успешна — подтверждаем (ACK) последнее сообщение в пачке с флагом multiple=true
		// Это подтвердит все сообщения до текущего deliveryTag включительно за один сетевой вызов
		lastDelivery := pendingDeliveries[len(pendingDeliveries)-1]
		if err := lastDelivery.Ack(true); err != nil {
			log.Printf("[ERROR] Ошибка отправки ACK в RabbitMQ: %v", err)
		}

		// 3. Очищаем буферы (сохраняя выделенную память)
		batch = batch[:0]
		pendingDeliveries = pendingDeliveries[:0]
	}

	for {
		select {
		case delivery, ok := <-deliveries:
			if !ok {
				// Канал закрыт (RabbitMQ отключился или сработал Graceful Shutdown)
				flush()
				return
			}

			// Парсим сообщение
			event := parseEvent(delivery.Body)
			batch = append(batch, event)
			pendingDeliveries = append(pendingDeliveries, delivery)

			// Если набрался полный батч — сбрасываем в БД
			if len(batch) >= c.batchSize {
				flush()
			}

		case <-ticker.C:
			// Сработал таймер — сбрасываем то, что успело набраться
			flush()

		case <-ctx.Done():
			// Получен сигнал SIGTERM/SIGINT (Graceful Shutdown)
			log.Println("[INFO] Получен сигнал отмены, сбрасываем остатки в ClickHouse...")
			flush()
			return
		}
	}
}

6. Вопросы и ответы с собеседований (FAQ)​

«Почему именно ClickHouse, а не PostgreSQL для хранения событий? Как устроен MergeTree и почему поштучный INSERT убивает базу?»​

Ответ: PostgreSQL — это строковая реляционная БД (OLTP), хранящая всю строку целиком на одной странице данных. При аналитических запросах (SUM, COUNT, AVG по датам за год) Postgres вынужден читать с диска все колонки, включая тяжелые текстовые поля, и быстро упирается в I/O и память.

ClickHouse — колоночная БД (OLAP). Каждая колонка хранится в отдельном сжатом файле. Аналитический запрос читает только 2–3 нужные колонки, сжатые в 5–10 раз благодаря однородности данных. Движки семейства MergeTree при каждом INSERT создают новую неизменяемую директорию (Data Part) с десятками файлов. Поштучный INSERT (1000 RPS) создает тысячи папок в секунду. Диск захлебывается от мелких IOPS, фоновый Merge не успевает склеивать куски, и БД падает с ошибкой Too many parts. Поэтому в ClickHouse обязательно писать батчами от 10 000 строк.

«Что произойдет, если воркер упадет (OOM Kill или SIGKILL) прямо во время записи батча в ClickHouse? Как гарантировать доставку At-least-once и бороться с дубликатами?»​

Ответ: Если воркер упал во время SaveBatch(), он не успеет отправить ACK в RabbitMQ. Сообщения останутся в очереди в статусе Unacked. Как только воркер (или его соседняя реплика) поднимется, RabbitMQ автоматически вернет эти сообщения в доставку (Redelivery). Гарантия At-least-once обеспечена.

Как бороться с дубликатами (Идемпотентность): Так как при сбоях сети сообщение может быть доставлено повторно, в ClickHouse дубликаты решаются двумя путями:

  1. Движок ReplacingMergeTree: Таблица создается с указанием версии (или timestamp). При фоновом слиянии (merge) ClickHouse автоматически удаляет дубликаты по первичному ключу ORDER BY, оставляя самую свежую запись.
  2. Дедупликация на вставке (INSERT Deduplication): ClickHouse автоматически запоминает хеши (MD5) всех вставленных блоков за последние пару часов. Если воркер повторно отправит ровно такой же батч с тем же токеном, ClickHouse молча проигнорирует дубликат. Плюс в событиях всегда сохраняется уникальный ExternalID / UUID для аналитической фильтрации (SELECT ... FROM events GROUP BY external_id).

«В Collector у вас буферизированный канал out := make(chan *Event, 100). Что будет, если RabbitMQ или ClickHouse начнут тормозить, и буфер заполнится?»​

Ответ: Когда буфер канала из 100 элементов полностью заполнится, все горутины, принимающие входящий HTTP-трафик (handler), заблокируются на записи в канал (out <- event). Это создает естественное обратное давление (Backpressure): HTTP-хендлеры перестают освобождаться, веб-сервер перестает принимать новые TCP-соединения, и передний балансировщик (nginx / API Gateway) начинает отдавать клиентам таймауты или HTTP 429/503. Это защищает сервис от перерасхода памяти (Out of Memory), так как мы не копим миллионы событий в неограниченных структурах. Если критично не блокировать клиентов, в коде используется select с default или time.After(), который при переполнении буфера сбрасывает менее важные метрики в лог.

«Как именно Worker Pool завершает работу при сигнале SIGTERM, если в памяти сейчас лежит буфер из 5000 событий, готовый к отправке?»​

Ответ: Реализуется паттерн Graceful Shutdown:

  1. При получении SIGTERM отменяется корневой контекст ctx.Done().
  2. Воркеры немедленно выходят из цикла чтения новых сообщений от RabbitMQ (или закрывается канал deliveries).
  3. Перед выходом из горутины вызывается функция flush(), которая берет все текущие накопленные в памяти 5000 событий и сбрасывает их в ClickHouse через финальный SaveBatch(context.Background(), batch) (важно использовать новый или неотмененный контекст с коротким таймаутом для финального сброса!).
  4. После успешного ответа от БД воркер отправляет ACK в RabbitMQ и вызывает wg.Done().
  5. Функция main() ждет wg.Wait() и только после завершения всех воркеров гасит процесс. Ни одно событие из памяти не теряется.
