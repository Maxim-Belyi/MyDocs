Индексы и оптимизация запросов

Индекс в базе данных — это вспомогательная структура данных, которая создается на основе одного или нескольких столбцов таблицы и предназначена для ускорения поиска, фильтрации и сортировки строк без необходимости выполнения полного сканирования таблицы (Full Table Scan / Seq Scan).

1. Устройство B-Tree и Hash индексов​

B-Tree (Сбалансированное дерево)​

Индекс типа B-Tree (или B+Tree) является типом индекса по умолчанию в большинстве реляционных СУБД (PostgreSQL, MySQL/InnoDB, Oracle).

  • Структура: Представляет собой иерархическое сбалансированное дерево поисковых страниц. Листовые узлы содержат отсортированные значения индексируемых колонок и ссылки (TID / Row ID) на физическое расположение строк на диске. В структуре B+Tree все листовые страницы дополнительно связаны между собой двунаправленным списком для быстрого последовательного чтения при сканировании диапазонов.
  • Поддерживаемые операции: Эффективно выполняет поиск по точному совпадению (=), поиск по диапазонам (<, <=, >, >=), проверку вхождения в список (IN), сортировку (ORDER BY) и поиск по текстовому префиксу (LIKE 'prefix%').
  • Асимптотическая сложность поиска: O(log N), где N — количество строк в таблице.

Hash-индекс​

Индекс, построенный на основе хеш-таблицы. Хеш-функция преобразует значение столбца в числовой хеш-код, который указывает на корзину (bucket) со ссылкой на строку таблицы.

  • Поддерживаемые операции: Работает исключительно для операций сравнения на строгое равенство (=, IN).
  • Ограничения: Не поддерживает поиск по диапазонам (>, <), сортировку и поиск по префиксу.
  • Сложность поиска: O(1) в среднем случае (при отсутствии массовых коллизий хеш-функции).

2. Составные индексы и порядок колонок​

Составной (многоколончатый) индекс создается по двум и более столбцам одной таблицы:

CREATE INDEX idx_orders_customer_status_date ON orders (customer_id, status, order_date);

Правило левого префикса (Leftmost Prefix Rule)​

СУБД может использовать составной индекс только в том случае, если в условиях фильтрации запроса (WHERE) используются столбцы, образующие непрерывный левый префикс определения индекса.

Для индекса (customer_id, status, order_date):

  • Будет использовать индекс:
    • WHERE customer_id = 10
    • WHERE customer_id = 10 AND status = 'paid'
    • WHERE customer_id = 10 AND status = 'paid' AND order_date > '2026-01-01'
  • НЕ будет использовать индекс (или использует только частично):
    • WHERE status = 'paid' (пропущена первая колонка customer_id)
    • WHERE order_date > '2026-01-01' (пропущены две левые колонки)
    • WHERE customer_id = 10 AND order_date > '2026-01-01' (будет использована только часть индекса по customer_id, а фильтрация по order_date выполнится перебором).

3. Селективность индекса​

Селективность (Selectivity) определяет отношение количества уникальных значений в столбце к общему количеству строк в таблице:

Селективность=COUNT(DISTINCT column)COUNT(*)\text{Селективность} = \frac{\text{COUNT(DISTINCT column)}}{\text{COUNT(*)}}Селективность=COUNT(*)COUNT(DISTINCT column)​
  • Высокая селективность (близко к 1 или 100%): Столбец содержит почти уникальные значения (например, user_id, email, UUID). Использование индекса по такому столбцу максимально эффективно, так как сразу отсекает 99.9% таблицы.
  • Низкая селективность (близко к 0): Столбец имеет всего несколько уникальных значений на миллионы строк (например, gender с 2 значениями или status с 4 статусами). Создание отдельного B-Tree индекса по низкоселективной колонке нецелесообразно: планировщик запросов (Query Planner) проигнорирует индекс и выберет полное сканирование таблицы (Seq Scan), чтобы избежать накладных расходов на случайное чтение диска по страницам индекса.

4. Чтение планов запросов: EXPLAIN ANALYZE​

Перед выполнением запроса СУБД строит план выполнения. Для анализа реального времени работы и используемых индексов применяется команда EXPLAIN ANALYZE (в PostgreSQL):

EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42 AND status = 'shipped';

Основные типы сканирования в выводе EXPLAIN​

  1. Seq Scan (Sequential Scan): Полное последовательное сканирование всей таблицы на диске от начала до конца. Индексы не используются. Нормально для маленьких таблиц или при выборке > 15-20% от общего объема строк.
  2. Index Scan: Поиск адресов строк в B-Tree индексе с последующим чтением самих страниц таблицы для извлечения данных всех запрошенных колонок.
  3. Index Only Scan (Покрывающий индекс): Идеальный вариант выполнения. Все запрашиваемые в SELECT столбцы уже содержатся внутри самого B-Tree индекса (или в INCLUDE секции индекса). СУБД читает только индекс, вообще не обращаясь к страницам основной таблицы на диске.
  4. Bitmap Index Scan + Bitmap Heap Scan: Применяется, когда индекс возвращает слишком много адресов строк. СУБД сначала сканирует индекс, строит в оперативной памяти битовую карту (Bitmap) нужных страниц диска, сортирует их по физическим адресам и затем читает страницы таблицы последовательно, минимизируя случайные переходы магнитной головки диска.
