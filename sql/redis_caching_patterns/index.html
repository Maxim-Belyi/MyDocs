Кеширование в Redis под высокой нагрузкой: Cache Stampede, Singleflight и Distributed Lock

При построении высоконагруженных микросервисов на Go, Redis используется как первый эшелон защиты реляционной базы данных (PostgreSQL/MySQL). Однако неправильное использование кеша в условиях 10 000+ запросов в секунду приводит к катастрофическим сбоям: лавинообразным обрушениям БД, блокировкам Event Loop в самом Redis и рассинхронизации данных между инстансами.

В этой статье мы разберем анатомию главных сбоев кеширования, устройство однопоточной модели Redis и реализуем на Go продакшен-паттерны защиты: Singleflight, Probabilistic Early Expiration (XFetch) и Redlock.

1. Анатомия сбоев: Cache Stampede и Cache Penetration​

Cache Stampede (Thundering Herd / Лавина запросов)​

Представьте, что главная страница интернет-магазина или данные популярного товара (item:42) лежат в Redis с TTL = 300 секунд. В момент 00:05:00 срок жизни ключа истекает, и он удаляется из кеша.

В эту же секунду на сервис приходит 10 000 одновременных запросов от клиентов.

  1. Все 10 000 горутин обращаются в Redis и получают redis.Nil (Cache Miss).
  2. Ни одна из горутин не знает, что остальные уже идут за данными. Все 10 000 горутин одновременно генерируют тяжелый SQL-запрос с JOIN и отправляют его в PostgreSQL.
  3. Пул подключений к БД (Connection Pool) мгновенно исчерпывается, процессор PostgreSQL уходит в 100%, память переполняется (OOM Killer), и база данных ложится.
[10 000 Клиентов] ──> [ Go-сервис (10k Горутин) ] ──(Cache Miss)──> [ Redis (Ключ истек) ]
                             │
                             ▼ (10 000 одновременных тяжелых SQL-запросов!)
                   [ PostgreSQL ──> CRASH / OOM ]

Cache Penetration (Пробитие кеша)​

Злоумышленник (или сбойный скрипт) начинает запрашивать данные по несуществующим ID (например, item:-1, item:999999999). Так как таких товаров нет ни в Redis, ни в PostgreSQL, при каждом запросе происходит Cache Miss, и сервис снова и снова идет в реляционную БД, пробивая кеш насквозь и перегружая диск напрасными поисками (Table Scan).

[!TIP] Решение Cache Penetration:

  1. Negative Caching (Кеширование пустых ответов): Если база данных вернула sql.ErrNoRows, мы сохраняем в Redis специальный маркер (например, строку "NULL") со слабым TTL (30–60 секунд). Повторный запрос по несуществующему ID остановится на уровне Redis.
  2. Bloom Filter (Фильтр Блума): Вероятностная структура данных в памяти Go или Redis, которая со 100% точностью говорит, что ключа точно нет в базе, и не пускает запрос дальше.

2. Почему KEYS * вешает продакшен (и почему нужен SCAN)​

Redis (до версии 6.0 полностью, а в 6.0+ — в части обработки команд) использует однопоточный Event Loop для выполнения команд от клиентов. Это означает, что в каждую долю секунды Redis выполняет ровно одну команду.

Ошибка: KEYS item:*​

Команда KEYS pattern работает со сложностью O(N)O(N)O(N), где NNN — общее количество ключей в базе данных. Если в вашем Redis лежит 50 миллионов ключей, выполнение KEYS займет несколько секунд. На эти несколько секунд однопоточный Event Loop полностью блокируется. Все остальные сервисы компании, пытающиеся сделать быстрый GET или SET, зависают по таймауту (context deadline exceeded).

Правильно: SCAN cursor [MATCH pattern] [COUNT count]​

Команда SCAN работает итеративно со сложностью O(1)O(1)O(1) за один шаг. Она возвращает порцию ключей (например, по 100 штук) и новый cursor для следующего шага. Между шагами SCAN Event Loop освобождается и успевает обработать тысячи входящих команд GET/SET от других клиентов.

3. Защита на уровне памяти Go: Singleflight​

Первая и самая эффективная линия обороны от Cache Stampede — пакет golang.org/x/sync/singleflight в стандартной экосистеме Go.

Идея: Если 10 000 горутин одновременно запросили item:42, Singleflight пропускает к базе данных только первую горутину. Остальные 9 999 горутин блокируются в ожидании. Когда первая горутина получает данные из PostgreSQL и складывает их в Redis, Singleflight раздаёт этот же результат из памяти всем 9 999 ожидающим горутинам. К базе данных выполняется ровно 1 запрос вместо 10 000.

Реализация безопасного кеширования на Go (go-redis + singleflight):​

package cache

import (
	"context"
	"database/sql"
	"encoding/json"
	"errors"
	"fmt"
	"time"

	"github.com/redis/go-redis/v9"
	"golang.org/x/sync/singleflight"
)

type Item struct {
	ID    int    `json:"id"`
	Title string `json:"title"`
	Price int    `json:"price"`
}

type ItemService struct {
	redis *redis.Client
	db    *sql.DB
	group singleflight.Group
}

const (
	nilMarker = "NULL_MARKER"
	itemTTL   = 5 * time.Minute
	nilTTL    = 30 * time.Second
)

func (s *ItemService) GetItem(ctx context.Context, itemID int) (*Item, error) {
	cacheKey := fmt.Sprintf("item:%d", itemID)

	// 1. Попытка получить из Redis
	cached, err := s.redis.Get(ctx, cacheKey).Result()
	if err == nil {
		// Проверка на Negative Cache (защита от Cache Penetration)
		if cached == nilMarker {
			return nil, errors.New("item not found")
		}
		var item Item
		if err := json.Unmarshal([]byte(cached), &item); err == nil {
			return &item, nil
		}
	} else if !errors.Is(err, redis.Nil) {
		// Логируем ошибку Redis, но не падаем (Деградация кеша: идем в БД)
		fmt.Printf("Redis error: %v\n", err)
	}

	// 2. Cache Miss: Используем Singleflight для защиты PostgreSQL от Stampede
	// Ключ в group.Do гарантирует, что для itemID выполнится только 1 вызов fetchFromDB
	result, err, _ := s.group.Do(cacheKey, func() (interface{}, error) {
		return s.fetchFromDBAndCache(ctx, cacheKey, itemID)
	})

	if err != nil {
		return nil, err
	}

	return result.(*Item), nil
}

func (s *ItemService) fetchFromDBAndCache(ctx context.Context, cacheKey string, itemID int) (*Item, error) {
	// Имитация запроса в PostgreSQL
	row := s.db.QueryRowContext(ctx, "SELECT id, title, price FROM items WHERE id = $1", itemID)

	var item Item
	err := row.Scan(&item.ID, &item.Title, &item.Price)
	if errors.Is(err, sql.ErrNoRows) {
		// Negative Caching: Кешируем отсутствие записи на 30 секунд
		_ = s.redis.Set(ctx, cacheKey, nilMarker, nilTTL).Err()
		return nil, errors.New("item not found")
	} else if err != nil {
		return nil, err
	}

	// Сохраняем успешный результат в Redis
	data, _ := json.Marshal(item)
	_ = s.redis.Set(ctx, cacheKey, data, itemTTL).Err()

	return &item, nil
}

4. Защита на уровне кластера: Probabilistic Early Expiration (XFetch)​

Singleflight защищает от одновременных запросов внутри одного инстанса (пода) Go-приложения. Но если в Kubernetes работает 100 подов вашего сервиса, при истечении TTL в базу пойдут 100 запросов (по одному от каждого пода).

Чтобы избежать даже этого, используется математический алгоритм Probabilistic Early Expiration (алгоритм XFetch).

Как работает XFetch?​

Ключ в Redis никогда не истекает «внезапно». При каждом чтении ключа мы вычисляем вероятность того, нужно ли обновить кеш заранее, в фоновом режиме, пока старый кеш еще валиден.

Чем ближе время к окончанию TTL, тем выше вероятность, что текущий клиент получит команду: «Верни старое значение пользователю прямо сейчас, но запусти фоновую горутину для обновления кеша в БД».

Формула проверки (обновить ли кеш прямо сейчас):

−β⋅Δ⋅ln⁡(rand())>TTLосталось-\beta \cdot \Delta \cdot \ln(\text{rand}()) > \text{TTL}_{\text{осталось}}−β⋅Δ⋅ln(rand())>TTLосталось​

Где:

  • Δ\DeltaΔ — время (в секундах), которое ушло на генерацию и сохранение этого кеша при прошлой записи (время запроса к БД).
  • β\betaβ — множитель жадности (обычно 1.01.01.0). Чем больше β\betaβ, тем раньше начнется фоновое обновление.
  • rand()\text{rand}()rand() — случайное число от 0 до 1.
  • TTLосталось\text{TTL}_{\text{осталось}}TTLосталось​ — сколько секунд осталось до физического удаления ключа в Redis.

[!NOTE] Благодаря XFetch пользователь никогда не ждет выполнения медленного запроса к БД при истечении кеша, а база данных не испытывает лавинообразных нагрузок, так как обновление происходит асинхронно в одной фоновой горутине задолго до реального удаления ключа.

5. Распределенные блокировки: Redlock (Distributed Lock)​

Когда нескольким независимым микросервисам нужно гарантировать эксклюзивный доступ к ресурсу (например, списание бонусов со счета пользователя или выполнение задачи по расписанию Cron), sync.Mutex в Go бессилен, так как сервисы работают на разных физических серверах.

В этом случае используется распределенная блокировка в Redis через атомарную команду SETNX (SET if Not eXists).

Золотое правило Distributed Lock​

Блокировка должна обладать тремя свойствами:

  1. Взаимоисключение: Только один клиент может удерживать блок в единицу времени.
  2. Защита от вечной блокировки (Deadlock Free): Если клиент захватил блок и упал (OOM Kill / отбой питания), блокировка обязана автоматически истечь по TTL.
  3. Безопасное удаление (Ownership): Клиент должен удалять только свою блокировку. Если операция длилась дольше TTL, блокировка истекла, и ее захватил другой сервис, первый клиент по окончании своей работы не должен случайно удалить чужую блокировку. Для этого в значение блокировки пишется уникальный UUID (токен владельца).

Реализация безопасного удаления через Lua-скрипт (Redlock pattern):​

В Redis проверка владельца (GET) и удаление (DEL) должны выполняться строго атомарно. Если сделать GET, а затем отдельной командой DEL, между ними может истечь TTL, и мы удалим чужой блок. Поэтому используется встроенный Lua-движок Redis:

package lock

import (
	"context"
	"crypto/rand"
	"encoding/hex"
	"errors"
	"time"

	"github.com/redis/go-redis/v9"
)

// Lua-скрипт гарантирует атомарность: удаляем ключ ТОЛЬКО если его значение равно нашему токену
const deleteLockLua = `
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
`

type DistributedLock struct {
	client *redis.Client
	key    string
	token  string
	ttl    time.Duration
}

func NewDistributedLock(client *redis.Client, key string, ttl time.Duration) *DistributedLock {
	// Генерируем уникальный токен для текущей операции
	b := make([]byte, 16)
	_, _ = rand.Read(b)
	token := hex.EncodeToString(b)

	return &DistributedLock{
		client: client,
		key:    key,
		token:  token,
		ttl:    ttl,
	}
}

// Acquire пытается захватить блокировку
func (l *DistributedLock) Acquire(ctx context.Context) (bool, error) {
	// NX = Set if Not Exists, PX = время жизни в миллисекундах
	ok, err := l.client.SetNX(ctx, l.key, l.token, l.ttl).Result()
	if err != nil {
		return false, err
	}
	return ok, nil
}

// Release атомарно освобождает блокировку, если мы все еще являемся ее владельцами
func (l *DistributedLock) Release(ctx context.Context) error {
	res, err := l.client.Eval(ctx, deleteLockLua, []string{l.key}, l.token).Result()
	if err != nil {
		return err
	}

	if res.(int64) == 0 {
		return errors.New("lock expired or owned by another client")
	}
	return nil
}

6. Вопросы с собеседований (FAQ)​

«Что будет с сервисом, если Redis внезапно упадет (или станет недоступен по сети)? Как правильно спроектировать отказ?»​

Ответ: Кеш Redis должен быть строго опциональным слоем (Graceful Degradation). Если Redis падает или отвечает ошибкой/таймаутом, Go-сервис не должен падать с HTTP 500. Ошибки Redis логируются в метрики (например, redis_errors_total), а сервис переключается на прямое чтение из PostgreSQL. При этом крайне важно, чтобы в этот момент была активна защита Singleflight, а пул соединений (pgxpool) имел жесткий лимит, чтобы упавший Redis не утащил за собой реляционную базу данных.

«Почему для Distributed Lock в production рекомендуется использовать алгоритм Redlock, а не просто SETNX на одном инстансе Redis?»​

Ответ: Одиночный инстанс Redis — это единая точка отказа (SPOF). Если мы используем Redis Sentinel или Cluster с асинхронной репликацией, возникает состояние гонки:

  1. Клиент А захватывает блокировку на Мастере.
  2. Мастер падает до того, как блокировка успела реплицироваться на Слейв.
  3. Слейв повышается до Мастера.
  4. Клиент Б запрашивает ту же блокировку на новом Мастере и успешно ее получает (так как записи на нем нет). В итоге два клиента одновременно удерживают эксклюзивный ресурс! Redlock решает эту проблему путем независимого захвата блокировок на нечетном количестве (N=5N=5N=5) независимых мастеров: блокировка считается полученной, только если удалось записать SETNX на большинстве (3 из 53\text{ из }53 из 5) нод за время, меньшее TTL.

«Чем отличается Cache Stampede от Cache Breakdown и Cache Penetration?»​

Ответ:

  • Cache Stampede (Thundering Herd): Ключ существовал, но его TTL истек, и тысячи клиентов одновременно идут за ним в БД.
  • Cache Breakdown: Частный случай Stampede для одного крайне «горячего» ключа (например, курс биткоина во время резкого скачка).
  • Cache Penetration: Клиенты массово запрашивают ключи, которых не существует вообще (ни в Redis, ни в БД). Решается через Negative Caching или Bloom Filter.
