# Подтверждение и отклонение сообщений (`Ack`, `Nack`, `Reject`)

Протокол AMQP 0-9-1 обеспечивает гарантированную доставку сообщений (At-Least-Once) посредством явных подтверждений со стороны приложения-получателя. Пока сообщение не подтверждено, оно сохраняется в брокере в статусе `Unacked` и привязано к конкретному каналу.

---

## 1. Методы подтверждения и отклонения

В библиотеке `amqp091-go` подтверждение или отклонение можно вызывать как через методы самого сообщения (`amqp.Delivery`), так и через методы канала (`amqp.Channel`). На практике удобнее использовать методы объекта сообщения, так как они автоматически используют нужные значения `DeliveryTag` и ссылки на канал.

### `msg.Ack(multiple bool)`
Положительное подтверждение успешной обработки. Брокер удаляет сообщение из очереди на диске/в памяти.
* `multiple = false`: Подтверждает только данное конкретное сообщение с текущим `DeliveryTag`.
* `multiple = true`: Подтверждает **все** сообщения в данном канале с номерами `DeliveryTag` от `1` до указанного включительно (пакетное подтверждение).

### `msg.Reject(requeue bool)`
Отклонение **одного конкретного** сообщения.
* `requeue = true`: Сообщение возвращается обратно в очередь брокера (в начало или конец в зависимости от версии брокера) и будет немедленно доставлено повторно текущему или другому свободному воркеру.
* `requeue = false`: Сообщение удаляется из текущей очереди. Если для очереди в `args` настроен обменник мертвых писем (`x-dead-letter-exchange`), сообщение автоматически пересылается в DLX. Если DLX не настроен, сообщение безвозвратно уничтожается.

### `msg.Nack(multiple bool, requeue bool)`
Расширение протокола от RabbitMQ (Negative Acknowledge). В отличие от `Reject`, поддерживает флаг `multiple`:
* `multiple = true`: Отклоняет целую пачку неподтвержденных сообщений вплоть до текущего `DeliveryTag`.
* `requeue = true/false`: Логика возврата или отправки в DLX аналогична `Reject`.

## 2. Безопасная обработка в цикле консьюмера

Пример корректной обработки различных типов ошибок с выбором соответствующего метода ответа:

```go
func processQueue(msgs <-chan amqp.Delivery) {
	for msg := range msgs {
		err := handleBusinessLogic(msg.Body)
		if err == nil {
			// Успешное выполнение
			_ = msg.Ack(false)
			continue
		}

		// Анализ типа ошибки
		if isValidationOrSyntaxError(err) {
			// Ошибка валидации JSON или бизнес-правил: повторная попытка бессмысленна.
			// Отправляем в Dead Letter Exchange (requeue = false)
			log.Printf("Некорректное сообщение [%s]: %v. Отправка в DLX", msg.MessageId, err)
			_ = msg.Reject(false)
		} else {
			// Временная ошибка (сбой сети, таймаут БД, блокировка):
			// Возвращаем в очередь для повторной обработки (requeue = true)
			log.Printf("Временный сбой для [%s]: %v. Возврат в очередь", msg.MessageId, err)
			_ = msg.Nack(false, true)
		}
	}
}
```

> **Опасность бесконечного цикла (Poison Message):** Использование `msg.Nack(false, true)` или `msg.Reject(true)` при ошибке валидации парсинга приведет к бесконечному циклу: сообщение вернется в очередь, мгновенно доставится снова, снова вызовет ошибку и снова вернется обратно, нагружая CPU на 100%. Ошибки парсинга всегда должны обрабатываться через `requeue = false`.

## 3. Обработка паник воркера (`defer` + `recover`)

В Go-приложениях аварийная паника в одной горутине-воркере без перехвата приведет к падению всего процесса сервиса. При потреблении сообщений критически важно оборачивать логику воркера в безопасный `recover`, чтобы при панике корректно отклонить сообщение и не заблокировать очередь:

```go
func safeWorker(msg amqp.Delivery) {
	defer func() {
		if r := recover(); r != nil {
			log.Printf("Критическая паника при обработке сообщения [%s]: %v", msg.MessageId, r)
			// При панике отклоняем сообщение без возврата в основную очередь (отправляем в DLX),
			// чтобы предотвратить повторное падение воркеров на «отравленном» сообщении.
			_ = msg.Reject(false)
		}
	}()

	// Вызов бизнес-логики, которая может вызвать panic(...)
	executeRiskyTask(msg.Body)

	// Если паники не произошло — подтверждаем
	_ = msg.Ack(false)
}
```

## 4. Что происходит при аварийном разрыве соединения

Если приложение аварийно завершается (`kill -9`, сбой питания, Out of Memory или обрыв сети) до того, как успевает отправить в канал фрейм `Ack`, `Nack` или `Reject`:
1. Брокер RabbitMQ обнаруживает разрыв TCP-соединения.
2. Все сообщения, которые находились в данном канале со статусом `Unacked`, автоматически переводятся брокером обратно в статус `Ready`.
3. Сообщения немедленно перераспределяются и доставляются другим подключенным консьюмерам этой очереди.
4. Каждому передоставленному сообщению в поле метаданных выставляется флаг `msg.Redelivered = true`.

### Архитектурное следствие: Идемпотентность
Наличие флага `Redelivered = true` и модель гарантии At-Least-Once обязывают разработчика делать всех консьюмеров **идемпотентными** (способными без последствий обрабатывать одно и то же сообщение повторно при проверке уникального `MessageId` в базе данных).
