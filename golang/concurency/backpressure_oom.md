# Backpressure и защита сервиса от OOM

Когда зависимость (база данных, брокер сообщений, внешний API) деградирует или работает медленно, сервис-производитель продолжает принимать новые запросы. Если не принять мер, накопленные в памяти задачи, горутины и объекты приведут к аварийному завершению процесса по `Out of Memory (OOM)`
---

## 1. Буферизованный канал как естественный Backpressure

Буферизованный канал является фундаментальным механизмом контроля давления между производителем и потребителем.

```go
out := make(chan *Event, 100)
```

Когда потребитель (воркер, пишущий в ClickHouse или RabbitMQ) замедляется, буфер постепенно заполняется. Как только буфер достигает ёмкости 100 элементов, **все горутины-производители блокируются** на записи `out <- event`. Это и есть обратное давление (Backpressure):

```
[HTTP-handler] → out <- event (блокируется) → [Channel buffer: 100/100] → [Worker → ClickHouse ↓ тормозит]
```

Следствия:
* HTTP-хендлеры перестают освобождаться.
* Веб-сервер (`net/http`) перестает принимать новые соединения из очереди TCP.
* Балансировщик (nginx / API Gateway) начинает получать таймауты и отдавать клиентам `HTTP 429` или `HTTP 503`.

Это **контролируемая деградация**: сервис не потребляет неограниченные объемы памяти, а давление передается наружу (клиентам), сигнализируя о проблеме.

---

## 2. Неблокирующая запись: `select` с `default`

Если блокировка хендлеров недопустима (например, для некритичной телеметрии), используется конструкция `select` с ветвью `default` — **паттерн неблокирующей записи (Non-blocking Send)**.

```go
select {
case out <- event:
    // Данные успешно записаны в буфер
default:
    // Буфер переполнен. Горутина НЕ блокируется — управление переходит сюда мгновенно.
    log.Warn("buffer overflow, event dropped")
    droppedEventsTotal.Inc() // Инкрементируем метрику сброшенных событий
}
```

**Когда применять:**
* Сбор некритичной телеметрии, счетчиков, логов аналитики, где допустима потеря 1-5% событий при пиковой нагрузке.
* Фоновые уведомления, push-события.

**Когда не применять:**
* Финансовые транзакции, события с гарантией At-Least-Once. Потеря данных в ветке `default` абсолютно недопустима.

## 3. Запись с таймаутом (`time.After` / `context`)

Компромисс между блокирующей и неблокирующей записью: сервис готов подождать место в буфере, но не бесконечно.

```go
func (h *handler) Handle(w http.ResponseWriter, r *http.Request) {
    select {
    case h.out <- event:
        // Успешно
    case <-time.After(50 * time.Millisecond):
        // Ждали 50 мс — место не освободилось
        http.Error(w, "Service Unavailable", http.StatusServiceUnavailable)
        return
    case <-r.Context().Done():
        // Клиент закрыл соединение, продолжать нет смысла
        return
    }
}
```

Предпочтительнее использовать таймер через `context.WithTimeout`, а не `time.After` в горячем пути, так как `time.After` создаёт новый объект таймера (и аллокацию) при каждом вызове и не позволяет его отменить досрочно:

```go
sendCtx, cancel := context.WithTimeout(r.Context(), 50*time.Millisecond)
defer cancel()

select {
case h.out <- event:
case <-sendCtx.Done():
    http.Error(w, "Service Unavailable", http.StatusServiceUnavailable)
}
```

## 4. Семафор: ограничение параллельных хендлеров

Буферизованный канал применяется не только для передачи данных, но и как **двоичный семафор** (Semaphore) для ограничения числа одновременно выполняемых операций.

```go
var sem = make(chan struct{}, 100) // Максимум 100 одновременно выполняемых запросов

func handler(w http.ResponseWriter, r *http.Request) {
    select {
    case sem <- struct{}{}: // Захватить слот
        defer func() { <-sem }() // Освободить слот в любом случае
    default:
        http.Error(w, "Too Many Requests", http.StatusTooManyRequests)
        return
    }
    // ... основная бизнес-логика
}
```

Это позволяет жестко ограничить потребление ресурсов (горутин, CPU, соединений с БД) вне зависимости от входящего трафика.

## 5. Worker Pool: фиксированный параллелизм

Антипаттерн — порождать горутину на каждое сообщение:

```go
// Антипаттерн: при 10 000 RPS создается 10 000 горутин/секунду
for msg := range msgs {
    go process(msg) // Бесконтрольный рост горутин
}
```

Каждая горутина стартует с 2-8 КБ стека (который может вырасти до мегабайт при глубоком стеке вызовов). Правильный подход — **фиксированный пул воркеров (Worker Pool)**:

```go
func StartWorkerPool(ctx context.Context, in <-chan *Event, workers int) {
    var wg sync.WaitGroup
    for i := 0; i < workers; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for {
                select {
                case event, ok := <-in:
                    if !ok {
                        return // Канал закрыт — выходим
                    }
                    process(event)
                case <-ctx.Done():
                    return
                }
            }
        }()
    }
    wg.Wait()
}
```

Фиксированное число горутин означает предсказуемый и ограниченный расход памяти.

## 6. `sync.Pool`: переиспользование объектов

При высокой частоте создания и уничтожения однотипных объектов (например, буферов `[]byte`, структур событий) сборщик мусора не успевает работать с ними, и heap растет. `sync.Pool` позволяет переиспользовать объекты вместо аллокации новых:

```go
var bufPool = sync.Pool{
    New: func() any {
        return make([]byte, 0, 4096)
    },
}

func processEvent(data []byte) {
    buf := bufPool.Get().([]byte)
    defer func() {
        buf = buf[:0]      // Сбрасываем длину, сохраняем ёмкость
        bufPool.Put(buf)   // Возвращаем в пул
    }()

    buf = append(buf, data...)
    // ... обработка
}
```

**Важно:** `sync.Pool` не гарантирует сохранность объектов между циклами GC — пул может быть очищен. Поэтому он подходит только для временных рабочих буферов, а не для долгоживущего состояния.

## 7. Лимит памяти рантайма (`GOMEMLIMIT`)

Начиная с Go 1.19, можно задать мягкий лимит потребления памяти для рантайма Go. Если потребление приближается к лимиту, рантайм начинает агрессивнее запускать GC, стараясь не допустить убийства процесса Linux OOM Killer:

```bash
# Задать лимит в переменной окружения (например, в Dockerfile или Kubernetes)
export GOMEMLIMIT=900MiB
```

Или программно:

```go
import "runtime/debug"

func init() {
    // Например, 90% от лимита контейнера в 1 GB
    debug.SetMemoryLimit(900 * 1024 * 1024)
}
```

**Отличие от `GOGC`:** `GOGC` задает порог роста heap (по умолчанию 100% — GC запускается, когда heap удвоился). `GOMEMLIMIT` задает абсолютный потолок и заставляет GC работать чаще при любом `GOGC`, если памяти не хватает.

## 8. Лимит на размер входящего запроса

Частая причина OOM — чтение всего тела HTTP-запроса в память при работе с загрузкой файлов или большими JSON-телами:

```go
// Ограничиваем тело запроса 1 МБ
r.Body = http.MaxBytesReader(w, r.Body, 1<<20)

// Используем потоковый декодер вместо json.Unmarshal
dec := json.NewDecoder(r.Body)
if err := dec.Decode(&payload); err != nil {
    http.Error(w, err.Error(), http.StatusBadRequest)
    return
}
```

## 9. Таймауты HTTP-сервера

Медленные или злоумышленные клиенты (Slowloris) могут держать горутину открытой бесконечно, постепенно исчерпывая ресурсы. Таймауты устанавливаются на уровне `http.Server`:

```go
srv := &http.Server{
    Addr:         ":8080",
    Handler:      mux,
    ReadTimeout:  5 * time.Second,  // Время на чтение всего запроса от клиента
    WriteTimeout: 10 * time.Second, // Время на отправку ответа клиенту
    IdleTimeout:  60 * time.Second, // Время keep-alive соединения в idle
}
```

## 10. Сводная таблица стратегий

| Стратегия | Применение | Что защищает |
| :--- | :--- | :--- |
| Буферизованный канал (Backpressure) | Все очереди производитель-потребитель | Память от роста накопленных задач |
| `select` с `default` (Drop) | Некритичная телеметрия, метрики | Хендлеры от блокировки |
| `select` с таймаутом | Умеренно важные события | Баланс между потерей данных и блокировкой |
| Семафор (`chan struct{}`) | Ограничение параллельных хендлеров | CPU, горутины, соединения с БД |
| Worker Pool | Фоновая обработка очередей | Бесконтрольный рост горутин |
| `sync.Pool` | Многократно создаваемые буферы/объекты | Давление на GC, heap |
| `GOMEMLIMIT` | Контейнерные окружения (K8s, Docker) | Убийство процесса OOM Killer |
| `http.MaxBytesReader` | HTTP API с загрузкой файлов/JSON | Память от больших тел запросов |
| `http.Server` Timeouts | Любой HTTP-сервер | Goroutine Leak от медленных клиентов |

---

## 11. Принцип выбора стратегии

* **Данные критичные (транзакции, платежи, медицинские события):** Применяется **блокирующий Backpressure**. Пусть клиент получит `HTTP 503` по таймауту — это лучше, чем молча удалить данные.
* **Данные некритичные (телеметрия, счетчики кликов, аналитика поведения):** Применяется **неблокирующий Drop** (`select default`) или сброс в локальный файловый буфер (Fallback to disk), чтобы не тормозить основной сервис ценой потери малой части данных.
