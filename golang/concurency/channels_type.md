# Типы каналов

### 1. Небуферизированные каналы (Unbuffered Channels)
Это каналы **без памяти**. По умолчанию, если вы создаете канал через `make(chan int)`, он является небуферизированным.

*   **Как это работает:** Отправитель и получатель должны встретиться в одной точке («рандеву»). Отправитель блокируется до тех пор, пока получатель не будет готов принять данные. Получатель блокируется до тех пор, пока отправитель не начнет передачу.
*   **Синхронизация:** Это не просто передача данных, это **полная синхронизация**. Вы точно знаете, что данные были успешно получены в момент отправки.

**Пример:**
```go
ch := make(chan string) // Небуферизированный канал

go func() {
    fmt.Println("Горутина: готова отправить...")
    ch <- "Привет!" // Зависает здесь, пока main не дойдет до чтения
    fmt.Println("Горутина: отправила!")
}()

time.Sleep(time.Second) // Имитация задержки в main
fmt.Println("Main: читаю из канала...")
msg := <-ch
fmt.Println("Main: получил", msg)
```
*Здесь горутина будет "висеть" на строке `ch <- "Привет!"`, пока `main` не дойдет до строки `<-ch`.*

### 2. Буферизированные каналы (Buffered Channels)
Это каналы с «памятью» (буфером) определенного размера. Мы создаем их, указывая емкость: `make(chan int, 3)`.

*   **Как это работает:** Отправитель может отправить данные в канал и **сразу идти дальше**, если в буфере есть свободное место. Получатель может забрать данные из буфера, даже если отправитель уже давно занят другими делами.
*   **Синхронизация:** Блокировка происходит **только** если буфер полон (для отправителя) или пуст (для получателя).

**Пример:**
```go
ch := make(chan int, 2) // Буфер на 2 элемента

ch <- 1 // Отправили, места еще есть, идем дальше
ch <- 2 // Отправили, буфер полон
fmt.Println("Main: отправил 2 числа, не дожидаясь получателя")

// Теперь кто-то другой может забрать данные позже
go func() {
    val := <-ch
    fmt.Println("Горутина: получила", val)
}()
```

---

### Сравнение: когда что использовать?

| Характеристика | Небуферизированный | Буферизированный |
| :--- | :--- | :--- |
| **Синхронизация** | Строгая (Rendezvous) | Свободная (Асинхронная) |
| **Память** | Не требует | Требует (выделяется под буфер) |
| **Безопасность** | Гарантирует доставку | Может привести к переполнению, если не читать быстро |
| **Применение** | Когда нужно точно знать, что задача выполнена | Когда нужно сгладить пики нагрузки (очередь) |

**Совет:**
*   Используйте **небуферизированные** каналы по умолчанию — это самый безопасный способ избежать «гонок» и убедиться, что процессы идут нога в ногу.
*   Используйте **буферизированные** каналы как «очередь» (например, если отправитель работает быстрее, чем получатель, и вы хотите избежать простоев отправителя). Будьте осторожны: если буфер бесконечно растет, а никто не читает, вы съедите всю память!

## 3. Направленные каналы (Directional Channels)

По умолчанию канал является **двунаправленным**: из него можно и читать, и писать. Но при передаче канала в функцию полезно ограничить его направление — это проверяется на этапе компиляции и делает код понятнее.

```go
// chan<- int  — только для записи (write-only)
// <-chan int  — только для чтения (read-only)

func producer(out chan<- int) { // Функция может только ПИСАТЬ в канал
    out <- 42
    // val := <-out  // Ошибка компиляции!
}

func consumer(in <-chan int) { // Функция может только ЧИТАТЬ из канала
    val := <-in
    fmt.Println("Получено:", val)
    // in <- 10  // Ошибка компиляции!
}

func main() {
    ch := make(chan int) // Двунаправленный
    go producer(ch)     // Go автоматически приводит chan int → chan<- int
    consumer(ch)        // Go автоматически приводит chan int → <-chan int
}
```

**Зачем это нужно?** Направленные каналы — это своеобразный контракт: мы на уровне типов гарантируем, что функция-producer никогда не прочтет из канала (и не закроет его ненароком, если не должна), а функция-consumer — не запишет. Это исключает целый класс ошибок на этапе компиляции, а не рантайма.

## 4. Поведение nil-канала и закрытого канала

Это один из самых частых вопросов на собеседованиях по Go. Нужно знать наизусть:

| Операция | Небуферизированный | Буферизированный | Nil-канал | Закрытый канал |
| :--- | :--- | :--- | :--- | :--- |
| **Запись** (`ch <- v`) | Блокируется, пока нет читателя | Блокируется, если буфер полон | Блокируется **навсегда** | **`panic`** |
| **Чтение** (`<-ch`) | Блокируется, пока нет записи | Блокируется, если буфер пуст | Блокируется **навсегда** | Возвращает zero-value, `ok = false` |
| **Закрытие** (`close(ch)`) | OK | OK | **`panic`** | **`panic`** |

### Как безопасно читать из канала, который может быть закрыт?

Используйте двухзначное присвоение — паттерн `comma ok`:

```go
val, ok := <-ch
if !ok {
    // Канал закрыт и пуст
    fmt.Println("Канал закрыт")
    return
}
fmt.Println("Получено:", val)
```

Или используйте цикл `for range` — он **автоматически** завершится, когда канал будет закрыт и опустеет:

```go
for val := range ch {
    fmt.Println("Получено:", val)
}
// Попадем сюда только после close(ch)
fmt.Println("Канал закрыт, цикл завершён")
```

### Важное правило

> **Закрывает канал тот, кто в него пишет (producer/sender), а не тот, кто читает (consumer/receiver).**

Если закрыть канал со стороны читателя, писатель получит `panic`. Закрытие канала — это сигнал читателям «данных больше не будет», а не «я перестаю читать».

## 5. Оператор select

`select` — это `switch` для каналов. Он ждет, пока один из `case`-ов не станет готов, и выполняет его.

```go
ch1 := make(chan string)
ch2 := make(chan string)

go func() { time.Sleep(1 * time.Second); ch1 <- "один" }()
go func() { time.Sleep(2 * time.Second); ch2 <- "два" }()

// Ждём первого, кто ответит
for i := 0; i < 2; i++ {
    select {
    case msg1 := <-ch1:
        fmt.Println("Получено из ch1:", msg1)
    case msg2 := <-ch2:
        fmt.Println("Получено из ch2:", msg2)
    }
}
```

### Ключевые особенности select

**1. Если несколько case готовы одновременно** — Go выбирает один **псевдослучайно** (чтобы ни один канал не «голодал»).

**2. Неблокирующий select с `default`:**
```go
select {
case msg := <-ch:
    fmt.Println("Получено:", msg)
default:
    // Канал пуст — сразу идём сюда, не блокируемся
    fmt.Println("Канал пуст, продолжаем работу")
}
```

**3. Таймаут через `time.After`:**
```go
select {
case result := <-slowOperation():
    fmt.Println("Успех:", result)
case <-time.After(3 * time.Second):
    fmt.Println("Таймаут: операция заняла слишком долго")
}
```

**4. Ожидание отмены через контекст (`ctx.Done()`):**
```go
select {
case data := <-dataCh:
    process(data)
case <-ctx.Done():
    fmt.Println("Контекст отменён:", ctx.Err())
    return
}
```

**5. Запись в `select`:**
`select` работает и для записи в канал, не только для чтения:
```go
select {
case ch <- value:
    fmt.Println("Записали в канал")
case <-done:
    fmt.Println("Отмена, не пишем")
}
```

## 6. Рекомендации по выбору размера буфера

Выбор правильного размера буфера — частый вопрос и источник багов.

- **Буфер = 0 (небуферизированный):** Строгая синхронизация. Используйте, когда важно, что получатель обработал данные перед тем, как отправитель продолжит работу.
- **Буфер = 1:** Позволяет отправителю не ждать, если получатель ещё не готов. Часто используется для сигнальных каналов (`chan struct{}`).
- **Буфер = N (размер очереди):** Используйте, когда знаете точное количество задач заранее (например, `make(chan Job, len(jobs))`), чтобы заполнить канал без блокировок и затем запустить воркеров.
- **Буфер = «магическое число»:** ❌ Антипаттерн. Если вы ставите буфер `1000` «на всякий случай», скорее всего, вы маскируете проблему проектирования, а не решаете её.
