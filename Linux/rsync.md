# Rsync

**`rsync` (Remote Sync)** — стандартный и самый мощный инструмент в Linux для синхронизации файлов и директорий. Он может работать как локально (между дисками), так и по сети (через SSH).

Главная фишка `rsync` — **дельта-алгоритм (Delta Transfer)**. 
При повторном копировании он не передает файлы целиком. Он вычисляет контрольные суммы и передает по сети **только измененные куски файлов** (или докачивает то, что оборвалось при прошлой передаче). Это колоссально экономит время и сетевой трафик.

---

## 1. Базовый набор флагов (`-avzP`)

Эта комбинация используется в 90% повседневных задач:

```bash
rsync -avzP ./my_project/ user@server.com:/var/www/my_project/
```

* **`-a` (`--archive`):** Архивный режим (режим «сделай всё как надо»). Включает в себя рекурсивное копирование всех вложенных папок, сохранение символических ссылок (`-l`), прав доступа (`-p`), времени модификации (`-t`), владельца (`-o`) и группы (`-g`).
* **`-v` (`--verbose`):** Подробный вывод в терминал списка обрабатываемых файлов.
* **`-z` (`--compress`):** Сжимает файлы на лету перед отправкой по сети и распаковывает на принимающей стороне (экономит трафик на текстах и коде, но нагружает CPU).
* **`-P` (`--progress` + `--partial`):** Показывает прогресс-бар для каждого отдельного файла и **сохраняет недокачанные файлы** при обрыве связи, позволяя мгновенно возобновить передачу с места обрыва при повторном запуске.

---

## 2. Проблема «Зомби-ядра» при миграции и флаг `--delete`

По умолчанию `rsync` работает по принципу **«только добавление и обновление»**. Он копирует новые файлы из источника и обновляет измененные, но **никогда не удаляет** файлы на целевом сервере (destination), если они исчезли из источника (source).

### Ловушка при обновлении фреймворков и библиотек
Представьте, что вы обновляете ядро фреймворка (например, Laravel, Bitrix или Django) со старой версии на новую.
1. В старом ядре был файл `core/old_module.php` и директория `legacy/`.
2. В новой версии разработчики фреймворка удалили эти файлы и переписали архитектуру.
3. Вы запускаете обычный `rsync -avz ./new_core/ /var/www/site/core/`.
4. **Результат — «Зомби-ядро»:** На сервере появились все новые файлы, но **старые файлы (`old_module.php`) остались лежать на месте!** В итоге в проекте одновременно живут два ядра (старое и новое), автозагрузчик классов (`autoloader`) сходит с ума, возникают фатальные конфликты зависимостей и трудноотловимые баги.

### Идеальное зеркалирование: `--delete`
Чтобы целевая папка стала **точной зеркальной копией** источника, обязательно добавляйте флаг `--delete`. Он заставляет `rsync` удалить на сервере всё, чего больше нет в источнике:

```bash
rsync -avzP --delete ./new_framework_core/ user@server:/srv/www/site/core/
```

> [!CAUTION]
> **Опасность флага `--delete`:**
> Если вы ошибетесь в пути или случайно укажете пустую исходную директорию, `rsync --delete` **безвозвратно удалит всё содержимое** целевой папки на боевом сервере! 
> Поэтому флаг `--delete` **всегда** нужно применять в паре с проверочным флагом `--dry-run`.

## 3. Сухой прогон (`--dry-run` / `-n`) — Ваша страховка

Перед выполнением любых деструктивных синхронизаций (особенно с флагами `--delete` или при сложном исключении папок) всегда выполняйте команду в режиме **сухого прогона (`--dry-run` или `-n`)**.

В этом режиме `rsync` полностью эмулирует свою работу: сканирует диски, сверяет контрольные суммы и выводит в терминал точный список файлов, которые будут созданы, обновлены или **удалены**, но **физически ничего на диске не меняет**.

```bash
# 1. Сначала делаем сухой прогон (смотрим, что удалится и скопируется)
rsync -avzP --delete --dry-run ./build/ root@server:/var/www/prod/

# Обратите внимание в выводе на строки с префиксом "deleting ..." — 
# это файлы, которые rsync собирается уничтожить на сервере!

# 2. Если вывод вас устраивает, убираем --dry-run и запускаем по-настоящему:
rsync -avzP --delete ./build/ root@server:/var/www/prod/
```

## 4. Главная ловушка пути: Слеш `/` на конце

Самая частая синтаксическая ошибка в `rsync` — неправильное понимание слеша `/` в конце пути **источника (Source)**.

### Вариант А: БЕЗ слеша (`./src`)
```bash
rsync -a /var/www/src /backup/dest
```
👉 **Скопирует САМУ директорию `src`.**
Внутри `/backup/dest` появится папка `src` с содержимым: **`/backup/dest/src/...`**.

### Вариант Б: СО слешем (`./src/`)
```bash
rsync -a /var/www/src/ /backup/dest
```
👉 **Скопирует СОДЕРЖИМОЕ директории `src`.**
Все файлы из `src` высыпятся прямо в корень назначения: **`/backup/dest/...`**.

> [!TIP]
> **Мнемоническое правило:**
> Слеш `/` на конце означает слово **«содержимое»**.
> * `/var/www/src` = папка `src`
> * `/var/www/src/` = содержимое папки `src`

## 5. Профессиональные «фишки» и флаги для продакшена

### 1. Безопасное удаление с бэкапом (`--backup` + `--backup-dir`)
Если вы используете `--delete` при деплое новой версии, но боитесь навсегда потерять удаляемые или заменяемые файлы, можно приказать `rsync` не уничтожать их, а **переместить в резервную директорию**:

```bash
rsync -avzP --delete \
  --backup --backup-dir=/var/www/old_releases/backup_$(date +%Y%m%d_%H%M%S) \
  ./dist/ root@server:/var/www/prod/
```
Теперь, если новый деплой сломает продакшен, все удаленные старые файлы и прошлые версии замененных файлов будут аккуратно сложены в папку `old_releases/backup_20260718_170000/`.

---

### 2. Исключение мусора (`--exclude` и `--exclude-from`)
При деплое проектов обязательно нужно исключать папки с кэшем, гитом и временными файлами.

```bash
rsync -avzP \
  --exclude='.git*' \
  --exclude='node_modules' \
  --exclude='vendor' \
  --exclude='*.log' \
  --exclude='bitrix/cache' \
  --exclude='bitrix/managed_cache' \
  ./project/ root@server:/srv/www/site/
```

Если исключений много, создайте отдельный файл `rsync-ignore.txt` (или используйте ваш `.gitignore`):
```bash
rsync -avzP --exclude-from='rsync-ignore.txt' ./project/ server:/path/
```

---

### 3. Ограничение скорости сети (`--bwlimit`)
Если вы перекачиваете базу данных в 500 ГБ или тяжелые медиафайлы на боевой сервер в середине рабочего дня, `rsync` без ограничений забьет весь сетевой канал сервера, и сайт перестанет открываться у клиентов.

Флаг `--bwlimit` задает лимит пропускной способности (в килобайтах или мегабайтах в секунду):
```bash
# Ограничить скорость передачи до 5 Мегабайт/сек
rsync -avzP --bwlimit=5M /data/backup/ root@server:/backups/
```

---

### 4. Обновление только новых файлов (`-u` / `--update`)
Если над директорией работают сразу несколько человек или систем, флаг `-u` приказывает `rsync` пропускать файлы, если на целевом сервере файл имеет **более свежую дату изменения**, чем в источнике (чтобы не затереть чужую новую работу старым файлом из локальной папки):

```bash
rsync -avzuP ./files/ root@server:/shared/files/
```

---

### 5. Фильтрация по размеру (`--max-size` и `--min-size`)
Полезно, если вы хотите скопировать код проекта, но случайно не утащить за собой огромные дампы баз данных (`.sql`), архивы или видеофайлы:

```bash
# Не передавать файлы, размер которых превышает 50 МБ
rsync -avzP --max-size=50M ./my_site/ root@server:/srv/site/
```

---

### 6. Нестандартный SSH порт и ключи (`-e`)
Если SSH на сервере висит не на стандартном 22 порту (например, на 2222) и требует конкретный приватный ключ:

```bash
rsync -avzP -e 'ssh -p 2222 -i ~/.ssh/deploy_key' ./build/ admin@server:/var/www/
```

---

## 6. Итоговый чек-лист безопасного деплоя/миграции через Rsync

1. **Проверьте слеши:** Убедитесь, что вы точно понимаете, копируете ли вы саму папку или её содержимое (`./dir` vs `./dir/`).
2. **Используйте сухой прогон (`--dry-run`):** Никогда не запускайте `--delete` на продакшене без предварительной проверки через `rsync -avzP --delete --dry-run ...`.
3. **Исключайте кэш и конфигурации:** Обязательно добавляйте `--exclude` для директорий кэша (`cache/`), сессий (`sessions/`) и локальных конфигов БД (`.env`, `bitrix/.settings.php`), чтобы деплой кода не затер боевые пароли и не перезаписал сессии пользователей.
4. **Очищайте зомби-файлы:** При обновлении ядра фреймворка или статики сборщика (Webpack/Vite) всегда используйте флаг `--delete`, чтобы удаленные в коде модули исчезали и на сервере.
