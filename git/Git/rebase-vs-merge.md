# Rebase vs Merge

Для объединения изменений из одной ветки в другую в Git применяются два основных механизма: `git merge` и `git rebase`. Оба подхода решают одну задачу, но формируют разную структуру истории коммитов.

---

## 1. Слияние через Git Merge

Команда `git merge` объединяет истории двух веток, создавая новый коммит слияния (merge commit), у которого есть два родителя.

```bash
git checkout main
git merge feature-branch
```

### Характеристики Merge
* **Сохранение полной истории:** Все коммиты сохраняются в исходном виде с оригинальными временными метками и авторами.
* **Неразрушающая операция:** История существующих веток не переписывается.
* **Недостаток:** При активной командной работе и частых слияниях граф истории (git log --graph) усложняется из-за множества переплетающихся линий и дополнительных merge-коммитов.

---

## 2. Перебазирование через Git Rebase

Команда `git rebase` переносит (перебазирует) коммиты текущей ветки на новое основание — вершину другой целевой ветки.

```bash
git checkout feature-branch
git rebase main
```

### Принцип работы
1. Git определяет общего предка текущей ветки (`feature-branch`) и целевой ветки (`main`).
2. Сохраняет во временную область патчи всех коммитов текущей ветки, созданных после общего предка.
3. Перемещает указатель текущей ветки на последний коммит целевой ветки (`main`).
4. Последовательно применяет сохраненные патчи по одному, создавая **новые коммиты** с новыми хешами для каждого изменения.

### Характеристики Rebase
* **Линейная история:** Граф коммитов остается абсолютно прямым и последовательным без дополнительных merge-коммитов.
* **Переписывание истории:** Изменяются хеши всех перенесенных коммитов, так как у них меняется родительский коммит.

---

## 3. Интерактивный режим (`git rebase -i`)

Интерактивный `rebase` предоставляет инструмент для глубокого редактирования истории локальных коммитов перед их публикацией на удаленный сервер.

```bash
# Редактирование последних N коммитов
git rebase -i HEAD~4

# Перебазирование относительно ветки main с интерактивным выбором
git rebase -i main
```

При запуске открывается текстовый редактор со списком коммитов и доступными командами для каждого из них:

* `pick` (или `p`): Оставить коммит без изменений (по умолчанию).
* `reword` (или `r`): Оставить изменения коммита, но изменить текст сообщения.
* `edit` (или `e`): Приостановить выполнение для внесения правок в файлы коммита.
* `squash` (или `s`): Объединить данный коммит с предыдущим (высшим в списке) и объединить их сообщения.
* `fixup` (или `f`): Объединить с предыдущим коммитом, но отбросить сообщение текущего коммита.
* `drop` (или `d`): Полностью удалить коммит из истории.

---

## 4. Золотое правило Rebase

> **Никогда не выполняйте `git rebase` для публичных веток (например, `main`, `develop`), которые уже отправлены на удаленный сервер и используются другими разработчиками.**

### Причина ограничения
Поскольку `rebase` создает новые хеши для существующих коммитов, история локального репозитория расходится с историей на удаленном сервере. Если другой разработчик уже стянул оригинальные коммиты, попытка объединить переписанную историю приведет к дублированию коммитов, сложным конфликтам и нарушению целостности проекта.

---

## 5. Сравнение и выбор стратегии

| Критерий | `git merge` | `git rebase` |
| :--- | :--- | :--- |
| **История коммитов** | Ветвистая, с сохранением исходного графа | Строго линейная, без коммитов слияния |
| **Изменение хешей** | Хеши существующих коммитов не меняются | Переносимые коммиты получают новые хеши |
| **Конфликты** | Разрешаются один раз при создании merge-коммита | Разрешаются последовательно на каждом переносимом коммите |
| **Применение** | Интеграция завершенных фич в `main`, работа с публичными ветками | Актуализация локальной `feature`-ветки перед Merge Request, очистка истории коммитов |
