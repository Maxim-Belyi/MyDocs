# Стек vs Куча (Stack vs Heap)

Управление оперативной памятью в современных программах базируется на разделении адресного пространства процесса на две фундаментальные области выделения памяти: Стек (Stack) и Кучу (Heap). Они различаются по структуре, механизмам аллокации, скорости доступа и правилам освобождения ресурсов.

---

## 1. Стек (Stack)

Стек — это область памяти, работающая по принципу LIFO (Last-In, First-Out). Он используется для хранения контекста выполнения функций, локальных переменных фиксированного размера, аргументов функций и адресов возврата.

### Принципы работы и особенности
* **Выделение и освобождение:** Выделение памяти на стеке выполняется автоматически при входе в функцию путем смещения указателя стека (Stack Pointer). При выходе из функции указатель смещается обратно, мгновенно освобождая всю память, занятую локальными переменными кадра стека (Stack Frame).
* **Скорость:** Аллокация и деаллокация требуют выполнения всего одной машинной инструкции (сдвиг регистра), что делает работу со стеком максимально быстрой.
* **Локализация данных (Cache Friendliness):** Данные на стеке расположены последовательно в смежных ячейках памяти. Это обеспечивает высокую эффективность использования L1/L2/L3-кэша процессора.
* **Ограничения размера:** Размер стека ограничен. При глубокой или бесконечной рекурсии возникает ошибка переполнения стека (`Stack Overflow`).

---

## 2. Куча (Heap)

Куча — это область памяти для динамического выделения данных, размер или время жизни которых неизвестны на этапе компиляции либо превышают область видимости одной функции.

### Принципы работы и особенности
* **Выделение и освобождение:** Выделение памяти в куче управляется аллокатором (например, `malloc` в C или встроенным аллокатором Go). Программа запрашивает блок памяти определенного размера, аллокатор ищет подходящую свободную область в таблицах свободных блоков и возвращает указатель на нее.
* **Скорость:** Выделение памяти в куче существенно медленнее, так как требует синхронизации (для потокобезопасности), поиска свободных сегментов и взаимодействия с операционной системой через системные вызовы (например, `mmap` или `brk`).
* **Управление ресурсами:** В языках без автоматического управления (C/C++) память должна освобождаться явно (`free`/`delete`). В управляемых языках (Go, Java) за очистку неиспользуемой памяти отвечает сборщик мусора (Garbage Collector).
* **Фрагментация:** При многократном выделении и освобождении блоков разного размера куча подвержена фрагментации: память разбивается на мелкие несмежные участки, что может затруднить выделение крупных сплошных массивов даже при наличии достаточного суммарного объема свободной памяти.

## 3. Сравнительная таблица Stack vs Heap

| Характеристика | Стек (Stack) | Куча (Heap) |
| :--- | :--- | :--- |
| **Принцип работы** | Линейная структура LIFO (Stack Frame) | Динамический граф / Таблицы свободных блоков |
| **Скорость аллокации** | Мгновенно (1 инструкция процессора) | Медленно (поиск блока, синхронизация, GC) |
| **Управление памятью** | Автоматически (при входе/выходе из функции) | Ручное (`free`) или автоматическое (Garbage Collector) |
| **Область видимости** | Локальная (в пределах вызова функции) | Глобальная (доступ по указателю из любой точки) |
| **Эффективность кэша CPU** | Высокая (пространственная локальность) | Низкая (объекты разбросаны по адресам) |
| **Фрагментация** | Отсутствует | Присутствует (внешняя и внутренняя фрагментация) |

## 4. Особенности в Go (Escape Analysis)

В языке Go программист не указывает явно, где именно (на стеке или в куче) должен быть размещен объект. Решение принимает компилятор во время сборки программы с помощью механизма **Escape Analysis (Анализ побега)**.

* **Размещение на стеке:** Если компилятор доказывает, что ссылка на переменную не выходит за пределы функции, создавшей эту переменную, она размещается на стеке (даже если создается через оператор `new`).
* **Размещение в куче (Escape to Heap):** Переменная «убегает» в кучу в следующих случаях:
  1. Указатель на локальную переменную возвращается из функции наружу.
  2. Переменная передается в интерфейсный аргумент функции (например, в `fmt.Println`), что требует динамической диспетчеризации.
  3. Переменная сохраняется в глобальную структуру данных или замыкание (Closure).
  4. Размер объекта слишком велик для размещения на стеке или неизвестен на этапе компиляции (например, срез с динамической длиной).
