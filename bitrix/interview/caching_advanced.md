# Кэширование: продвинутые сценарии

Базовые типы кэша описаны в отдельной статье. Здесь — тегированный кэш, сравнение хранилищ и принцип работы Композитного сайта.

---

## 1. Тегированный кэш (TaggedCache)

Тегированный кэш — способ инвалидировать сразу группу кэш-записей по общему признаку, не зная их конкретных ключей.

### Принцип работы

1. При записи в кэш регистрируется один или несколько **тегов** (произвольных строк-идентификаторов).
2. При изменении данных вызывается инвалидация по тегу.
3. Все кэш-записи, зарегистрированные с этим тегом, удаляются.

### Пример использования

```php
$cache = \Bitrix\Main\Data\Cache::createInstance();
$taggedCache = \Bitrix\Main\Application::getInstance()->getTaggedCache();

$cacheKey  = 'user_orders_' . $userId;
$cacheDir  = '/user_orders/';
$cacheTtl  = 3600;

if ($cache->initCache($cacheTtl, $cacheKey, $cacheDir)) {
    // Данные из кэша
    $orders = $cache->getVars();
} else {
    $cache->startDataCache();
    $taggedCache->startTagCache($cacheDir);

    // Регистрируем тег — этот кэш связан с инфоблоком #5
    $taggedCache->registerTag('iblock_id_5');
    // Можно регистрировать несколько тегов
    $taggedCache->registerTag('user_id_' . $userId);

    $orders = /* ... запрос к БД ... */ [];

    $taggedCache->endTagCache();
    $cache->endDataCache($orders);
}
```

### Сброс кэша по тегу

```php
// Сброс всего кэша, помеченного тегом iblock_id_5
$taggedCache = \Bitrix\Main\Application::getInstance()->getTaggedCache();
$taggedCache->clearByTag('iblock_id_5');
```

Битрикс делает это автоматически, если элемент инфоблока изменяется через API (`CIBlockElement::Update`, `CIBlockElement::Add`). Тег формируется по правилу `iblock_id_{ID}`.

### Теги для часто используемых сущностей

| Тег | Когда инвалидируется |
| :--- | :--- |
| `iblock_id_5` | Изменение любого элемента в инфоблоке 5 |
| `iblock_new_element` | Добавление нового элемента в любой инфоблок |
| `USER_GROUPS` | Изменение групп пользователей |

## 2. Хранилища кэша

Хранилище настраивается в `/bitrix/.settings.php` в секции `cache`.

### Файловый кэш (по умолчанию)

```php
'cache' => [
    'value' => [
        'type' => 'file',
    ],
],
```

- Данные пишутся в файлы в `/bitrix/cache/` и `/bitrix/managed_cache/`.
- Работает без дополнительных зависимостей.
- При большом числе файлов файловая система начинает тормозить (inodes, dentry cache).

### Memcached

```php
'cache' => [
    'value' => [
        'type'     => 'memcache',
        'host'     => 'localhost',
        'port'     => '11211',
    ],
],
```

- Данные хранятся в оперативной памяти, очень быстро.
- При перезапуске сервера весь кэш теряется (нет персистентности).
- Не поддерживает тегированный кэш нативно: Битрикс эмулирует теги через дополнительные ключи.

### Redis

```php
'cache' => [
    'value' => [
        'type'      => 'd',
        'extension' => 'redis',
        'host'      => 'localhost',
        'port'      => '6379',
    ],
],
```

- Данные в памяти, опционально сохраняются на диск (RDB/AOF).
- Нативно поддерживает структуры данных: списки, множества, хэши.
- Позволяет корректно реализовать тегированный кэш через множества (sets).
- Предпочтительный вариант для высоконагруженных проектов.

### Сравнение хранилищ

| Параметр | Файлы | Memcached | Redis |
| :--- | :--- | :--- | :--- |
| Скорость | Средняя | Высокая | Высокая |
| Персистентность | Да (диск) | Нет | Опционально |
| Тегированный кэш | Да | Эмуляция | Да |
| Кластеризация | Нет | Да | Да |
| Доп. зависимости | Нет | PHP-расширение | PHP-расширение |
| Рекомендован для | Небольшие сайты | Средние проекты | Highload |

## 3. Управляемый кэш и TTL

В Битрикс принято ставить **большое значение TTL** (вплоть до нескольких лет), потому что управляемый кэш сам удаляет записи при изменении данных через API.

```php
// В xpage.core — кэш метаданных инфоблока на 8 лет
private static int $ttl = 8 * 365 * 24 * 60 * 60;
```

Логика: если данные меняются только через админку и это — редкое событие, нет смысла сбрасывать кэш раз в час. Управляемый кэш очистится автоматически при следующем сохранении.

## 4. Композитный сайт

Уникальная технология Битрикс для максимальной скорости отдачи страниц пользователю.

### Проблема

Страница содержит как статичные данные (каталог, SEO-тексты), так и динамические (имя пользователя, корзина, баннер «скидка для вас»). Кэшировать страницу целиком нельзя — динамика будет одинаковой для всех.

### Решение: разделение страницы

1. Битрикс отдаёт пользователю **статичный HTML-каркас** немедленно (из кэша). Время ответа — десятки миллисекунд.
2. Динамические блоки (компоненты, помеченные как «не кэшируемые») **заменяются заглушками**.
3. JavaScript на стороне браузера отправляет **отдельный AJAX-запрос** за динамическим контентом.
4. Заглушки заменяются реальными данными.

### Как включить для компонента

```php
// В component.php или class.php
$this->setFrameMode(true); // Компонент работает в frame-режиме
```

Компоненты, помеченные `setFrameMode(true)`, при повторных запросах страницы не выполняются в основном потоке — их данные подгружаются отдельно.

### Ограничения

- Не работает с авторизованными пользователями по умолчанию (для них страница генерируется заново).
- Требует настройки на уровне сайта и корректной разметки компонентов.
- Динамический контент должен быть вынесен в отдельные компоненты.

## Итог

| Задача | Инструмент |
| :--- | :--- |
| Сброс кэша при изменении элемента инфоблока | Тегированный кэш, тег `iblock_id_{N}` |
| Сброс кэша по группе записей | `$taggedCache->clearByTag('...')` |
| Максимальная скорость на highload | Redis как хранилище |
| Мгновенная отдача статичных страниц | Композитный сайт |
| Кэш данных с ручным управлением | `\Bitrix\Main\Data\Cache` |
