Сети: TCP, UDP, HTTP, REST API

Этот материал охватывает вопросы о базовых сетевых протоколах, которые регулярно встречаются на собеседованиях, особенно на уровне Middle и выше.

Ключ к пониманию — это модель слоёв. Данные в интернете упаковываются как матрёшка: каждый слой не знает про внутренности другого и делает только свою работу.

[ Прикладной уровень ]   HTTP, HTTPS, FTP, SMTP, DNS
[ Транспортный уровень ] TCP  или  UDP
[ Сетевой уровень ]      IP (Internet Protocol)
[ Физический уровень ]   Провода, Wi-Fi, оптоволокно

1. TCP vs UDP (Транспортный уровень)​

Оба протокола делают одно и то же — доставляют данные от компьютера А к компьютеру Б. Но делают это принципиально разными способами.

TCP — «Ответственный курьер»​

Перед отправкой данных компьютеры «здороваются» (устанавливают соединение — three-way handshake). TCP нумерует каждый пакет, получатель подтверждает получение, а если пакет потерялся — отправитель пришлет его снова.

Гарантирует: целостность данных, правильный порядок пакетов. Плата за это: небольшая задержка из-за подтверждений.

Где используется: везде, где важна точность.

  • Загрузка сайтов (HTTP/HTTPS)
  • Скачивание файлов
  • Отправка email (SMTP)
  • Банковские операции

UDP — «Пулемёт»​

UDP просто выстреливает пакетами данных в сторону получателя. Он не проверяет, дошли ли они, не ждёт подтверждений, не переотправляет потерянное. Из-за этого он работает значительно быстрее.

Где используется: там, где скорость важнее 100% точности.

  • Онлайн-игры (CS2, Dota 2) — лучше пропустить один кадр, чем лагать
  • Видеосвязь (Zoom, Google Meet) — один потерянный кадр незаметен
  • DNS-запросы — короткий вопрос, не нужно устанавливать соединение
  • Видеостриминг (YouTube, Twitch)

Сравнение​

TCPUDP
НадёжностьГарантированная доставкаБез гарантий
СкоростьМедленнееБыстрее
СоединениеУстанавливает (handshake)Не устанавливает
Порядок пакетовГарантированНе гарантирован
ПрименениеВеб, файлы, emailИгры, видео, DNS

2. HTTP vs HTTPS (Прикладной уровень)​

Если TCP — это дорога, то HTTP — это правила упаковки груза. HTTP работает поверх TCP.

HTTP — «Открытая почтовая карточка»​

Браузер отправляет текстовый запрос: GET /index.html. Сервер отвечает: 200 OK и прикладывает HTML-код страницы.

Главный минус: все данные летят по проводам в открытом читаемом виде. Любой, кто «сидит» в том же публичном Wi-Fi, может видеть всё что вы отправляете — пароли, сообщения, данные карты.

HTTPS — «Запечатанный сейф»​

Это тот же самый HTTP, но завёрнутый в криптографический туннель (протокол TLS/SSL). Перед отправкой данных браузер и сервер обмениваются сертификатами и «договариваются» о ключах шифрования. Если хакер перехватит трафик — он увидит лишь бессмысленный набор символов.

Сегодня HTTPS — это абсолютный стандарт для любого сайта. Браузеры помечают HTTP-сайты как «Небезопасные».

HTTP/1.1, HTTP/2 и HTTP/3​

ВерсияТранспортКлючевая особенность
HTTP/1.1TCPОдин запрос за раз на соединение
HTTP/2TCPМультиплексирование: много запросов в одном соединении
HTTP/3UDP (QUIC)Решает проблему «блокировки очереди» TCP

HTTP/3 и UDP — это интересная история. TCP имеет проблему: если один пакет потерялся, вся очередь останавливается и ждёт его («Head-of-line blocking»). При плохом мобильном интернете это сильно замедляет сайты.

Инженеры Google (а потом это стало мировым стандартом) взяли быстрый UDP, но добавили к нему собственную логику надёжности прямо внутри протокола QUIC. В HTTP/3 пакеты едут независимо — если один потерялся, остальные не ждут.

3. HTTP-методы (Глаголы)​

HTTP-методы — это «глаголы», которые говорят серверу, что именно клиент хочет сделать с ресурсом.

Основные методы (CRUD)​

МетодДействиеАналог в SQLПример
GETПолучить данныеSELECTGET /api/users
POSTСоздать ресурсINSERTPOST /api/users
PUTПолностью заменить ресурсUPDATE (все поля)PUT /api/users/5
PATCHЧастично обновить ресурсUPDATE (одно поле)PATCH /api/users/5
DELETEУдалить ресурсDELETEDELETE /api/users/5

Частая ошибка на собеседовании!​

Метода UPDATE в HTTP не существует!

Разработчики часто путают SQL (UPDATE) и HTTP. В стандарте HTTP нет метода UPDATE. Для обновления используются PUT и PATCH.

В чём разница между PUT и PATCH?​

  • PUT — Полная замена. Вы должны передать все поля ресурса. Если у пользователя есть name, email, age, а вы отправите PUT только с name — сервер обнулит email и age.
  • PATCH — Хирургический инструмент. Передаете только то поле, которое хотите изменить. Остальные поля остаются нетронутыми.

Служебные методы (для продвинутых)​

  • OPTIONS — браузер отправляет его автоматически до основного запроса, если frontend (site.com) и API (api.site.com) на разных доменах. Он спрашивает у сервера: «Разрешено ли мне сюда обращаться?». Это механизм безопасности CORS.
  • HEAD — то же, что GET, но сервер возвращает только заголовки, без тела ответа. Полезно, чтобы узнать размер файла или проверить существование ресурса, не скачивая его.

4. REST API (Архитектурный стиль)​

REST (Representational State Transfer) — это набор правил (архитектурный стиль) о том, как правильно строить API поверх HTTP. Это не стандарт и не протокол — это соглашение о хорошем тоне.

Ключевые принципы REST​

1. Всё строится вокруг ресурсов (существительных)

Ресурс — это любая сущность: пользователь, статья, заказ. URL ресурса всегда строится через существительное во множественном числе. Действие передается через HTTP-метод.

// Плохо (не REST):
GET /getUsers
POST /createUser
POST /deleteUser?id=5

// Хорошо (REST):
GET /api/users          // Получить список пользователей
GET /api/users/5        // Получить пользователя #5
POST /api/users         // Создать пользователя
PUT /api/users/5        // Полностью обновить пользователя #5
PATCH /api/users/5      // Частично обновить пользователя #5
DELETE /api/users/5     // Удалить пользователя #5

2. Без состояния (Stateless)

Сервер не запоминает ничего о предыдущих запросах. Каждый запрос должен содержать всё необходимое, чтобы сервер мог его обработать (например, токен авторизации в заголовке).

// Каждый запрос содержит токен — сервер не хранит сессию
GET /api/orders
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

3. Единый интерфейс

Независимо от того, что за клиент обращается (мобильное приложение, браузер, другой сервис) — API выглядит одинаково.

4. Коды ответа HTTP

REST API общается через стандартные HTTP-коды:

КодЗначение
200 OKВсё хорошо, данные в ответе
201 CreatedРесурс успешно создан
204 No ContentВсё хорошо, данных в ответе нет (например, после DELETE)
400 Bad RequestКлиент передал неверные данные
401 UnauthorizedНужна авторизация (токен не передан или устарел)
403 ForbiddenАвторизован, но нет прав (не ваш ресурс)
404 Not FoundРесурс не найден
422 Unprocessable EntityДанные не прошли валидацию (часто в Laravel)
500 Internal Server ErrorОшибка на стороне сервера

REST vs другие подходы​

Помимо REST существуют другие способы строить API:

  • GraphQL — клиент сам указывает, какие именно поля хочет получить. Гибко, но сложнее.
  • gRPC — высокоскоростной протокол на бинарном формате (protobuf). Используется для общения между микросервисами внутри серверной инфраструктуры.

Резюме​

  • TCP — надёжно, с подтверждениями. Используется для веба, файлов, email.
  • UDP — быстро, без гарантий. Используется для игр, видео, DNS.
  • HTTP — язык общения браузера и сервера (поверх TCP). HTTP/3 — исключение, работает поверх UDP (QUIC).
  • HTTPS — HTTP внутри зашифрованного TLS-туннеля. Абсолютный стандарт сегодня.
  • REST — архитектурный стиль построения API: ресурсы как существительные, действия как HTTP-методы, без состояния.
  • UPDATE в HTTP не существует — только PUT (полная замена) и PATCH (частичное обновление).
