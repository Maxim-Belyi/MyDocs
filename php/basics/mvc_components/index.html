Модель, Контроллер, Провайдер, Репозиторий

1. Модель (Model) — «Работа с данными»​

Модель отвечает за данные. В Laravel (через Eloquent) каждая модель напрямую связана с конкретной таблицей в базе данных. Её главная задача — извлекать, сохранять и обновлять информацию, а также описывать связи между таблицами (отношения: один-ко-многим, многие-ко-многим и т.д.).

Модель вообще ничего не знает о том, откуда пришел запрос (из браузера или по API) — она занимается исключительно правилами работы с данными.

// Модель User автоматически связана с таблицей `users`
class User extends Model
{
    // Всё! Eloquent сам умеет делать find(), save(), delete() и т.д.
}

// Использование в контроллере:
$user = User::find(1);   // Найти пользователя по ID
$user->name = 'Максим'; // Изменить данные
$user->save();           // Сохранить в БД

Аналогия: Складской работник. Ему говорят «дай товар №5» или «положи это на полку» — он точно знает, как это сделать по правилам склада. Но ему всё равно, кто из менеджеров отдал приказ.

2. Контроллер (Controller) — «Посредник»​

Контроллер — это связующее звено между HTTP-запросом пользователя и внутренностями приложения. Его задача — принять запрос от роутера, запустить валидацию входящих данных, попросить Модель достать или сохранить нужные данные, а затем решить, что вернуть пользователю: отрендерить HTML-шаблон, сделать редирект или отдать JSON.

Хорошим тоном считается делать контроллеры "тонкими" — не писать в них сложные расчеты и бизнес-логику. Это работа для Сервисов или Моделей. Контроллер — лишь регулировщик движения.

class UserController extends Controller
{
    // Принял запрос → попросил Модель → вернул View
    public function show(int $id)
    {
        $user = User::findOrFail($id); // Делегируем работу Модели
        return view('users.profile', compact('user')); // Отдаем View
    }
}

Аналогия: Официант в ресторане. Он принимает заказ у клиента (запрос), передает его на кухню (Модели), забирает готовое блюдо и красиво подает клиенту на стол (View). Сам он ничего не готовит.

3. Сервис-провайдер (Service Provider) — «Настройщик при запуске»​

Сервис-провайдеры — это сердце загрузки приложения Laravel. Они запускаются в самом начале, ещё до того, как HTTP-запрос дойдет до роутера и контроллера.

В провайдерах приложение «готовится» к работе:

  • Регистрируются сторонние пакеты.
  • Связываются интерфейсы с их реализациями в Service Container.
  • Настраиваются глобальные события и очереди.
  • Регистрируются глобальные переменные для шаблонов (через View::share()).
class AppServiceProvider extends ServiceProvider
{
    // register() — связать интерфейс с реализацией
    public function register(): void
    {
        $this->app->bind(
            UserRepositoryInterface::class,
            EloquentUserRepository::class
        );
    }

    // boot() — выполнить что-то после того, как всё зарегистрировано
    public function boot(): void
    {
        User::observe(UserObserver::class);
    }
}

Аналогия: Команда подготовки ресторана перед открытием. До того как придет первый клиент (запрос), они включают свет, настраивают кассовые аппараты, расставляют столы. Когда ресторан открывается — всё уже готово.

4. Репозиторий (Repository) — это НЕ то же самое, что Модель!​

Это очень частая путаница. На собеседовании за неё могут «зацепиться».

Модель в Laravel — паттерн Active Record​

Модели в Laravel реализуют паттерн Active Record: объект содержит и сами данные (имя, email), и методы для работы с базой (save(), delete()). Модель знает, что она является строкой в таблице базы данных.

$user = User::find(1); // Модель сама себя ищет
$user->name = 'Максим';
$user->save();         // Модель сама себя сохраняет

Репозиторий — паттерн Repository​

Репозиторий — это слой абстракции, который прячет логику работы с базой данных от бизнес-логики. В идеальном мире паттерна Repository сам объект данных (сущность) вообще не умеет сохранять себя в базу. Он просто хранит свойства. А достает и сохраняет его именно Репозиторий.

// Интерфейс — "контракт" для любой реализации
interface UserRepositoryInterface
{
    public function findById(int $id): ?User;
    public function save(User $user): User;
}

// Реализация через Eloquent
class EloquentUserRepository implements UserRepositoryInterface
{
    public function findById(int $id): ?User
    {
        return User::find($id);
    }

    public function save(User $user): User
    {
        $user->save();
        return $user;
    }
}

// Использование в сервисе:
$user = $userRepository->findById(1); // Просим репозиторий
$user->name = 'Максим';
$userRepository->save($user);         // Репозиторий сохраняет

Ключевая разница​

Модель (Active Record)Репозиторий
Что умеетХранит данные + умеет сохранять себяТолько извлекает и сохраняет объекты
Привязка к БДЖёсткая (знает про таблицу)Нет (работает с абстрактным объектом)
СложностьПросто, из коробки LaravelНужно писать вручную
Когда использовать90% проектовКрупные проекты, DDD, смена ORM

Мнение индустрии: Многие считают, что делать паттерн Repository поверх Eloquent — это излишнее усложнение (overengineering), потому что Eloquent сам по себе уже предоставляет отличные методы для запросов. Репозитории стоит использовать только в очень крупных проектах (DDD) или если вы точно знаете, что будете менять базу данных (с MySQL на MongoDB). Для 90% проектов моделей более чем достаточно.

Резюме​

  • Модель — представление строки из БД. Хранит данные и умеет себя сохранять (Active Record).
  • Контроллер — регулировщик. Принимает HTTP-запрос, делегирует работу Моделям/Сервисам, возвращает ответ.
  • Сервис-провайдер — стартует при запуске приложения, ещё до любых запросов. Регистрирует зависимости и настраивает сервисы.
  • Репозиторий — дополнительный слой абстракции над хранилищем данных. В Laravel не обязателен и нужен только в специфических случаях.
