Паттерны проектирования в PHP/Laravel

Паттерны — это типовые решения повторяющихся задач. В контексте PHP и Laravel наиболее востребованы Repository, Service Layer, DTO и Factory. Все примеры построены на реалистичных сценариях с Eloquent.

1. Repository Pattern​

Цель: изолировать логику доступа к данным от бизнес-логики. Бизнес-слой работает только с интерфейсом репозитория и не знает, откуда берутся данные (Eloquent, массив, внешний API).

// Интерфейс (контракт)
interface UserRepositoryInterface
{
    public function findById(int $id): ?User;
    public function findByEmail(string $email): ?User;
    public function save(User $user): User;
    public function delete(int $id): bool;
    /** @return User[] */
    public function findActive(): array;
}

// Eloquent-реализация
class EloquentUserRepository implements UserRepositoryInterface
{
    public function findById(int $id): ?User
    {
        return User::find($id);
    }

    public function findByEmail(string $email): ?User
    {
        return User::where('email', $email)->first();
    }

    public function save(User $user): User
    {
        $user->save();
        return $user;
    }

    public function delete(int $id): bool
    {
        return User::destroy($id) > 0;
    }

    public function findActive(): array
    {
        return User::where('is_active', true)->get()->all();
    }
}

// Биндинг в Service Provider
class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->app->bind(
            UserRepositoryInterface::class,
            EloquentUserRepository::class
        );
    }
}

Преимущества:

  • Упрощает тестирование: можно подменить реализацию на InMemoryUserRepository.
  • При переходе с Eloquent на другой ORM меняется только реализация, не бизнес-логика.

2. Service Layer​

Цель: выделить бизнес-логику из контроллера в отдельный класс. Контроллер принимает HTTP-запрос, делегирует работу сервису и возвращает ответ.

class UserService
{
    public function __construct(
        private UserRepositoryInterface $users,
        private Mailer $mailer,
    ) {}

    public function register(RegisterUserDto $dto): User
    {
        // Проверка: email не занят
        if ($this->users->findByEmail($dto->email) !== null) {
            throw new \DomainException("Email '{$dto->email}' is already registered");
        }

        // Создание пользователя
        $user = new User();
        $user->name  = $dto->name;
        $user->email = $dto->email;
        $user->password = bcrypt($dto->password);

        $user = $this->users->save($user);

        // Отправка приветственного письма
        $this->mailer->send(
            new WelcomeEmail($user->email, $user->name)
        );

        return $user;
    }

    public function deactivate(int $userId): void
    {
        $user = $this->users->findById($userId);
        if ($user === null) {
            throw new \DomainException("User $userId not found");
        }

        $user->is_active = false;
        $this->users->save($user);
    }
}

// Тонкий контроллер — только HTTP-слой
class UserController extends Controller
{
    public function __construct(private UserService $service) {}

    public function register(RegisterRequest $request): JsonResponse
    {
        $dto = RegisterUserDto::fromRequest($request);
        $user = $this->service->register($dto);

        return response()->json(new UserResource($user), 201);
    }
}

3. DTO (Data Transfer Object)​

Цель: передавать данные между слоями в виде типизированных объектов, а не массивов или Request-объектов. DTO — неизменяемый (immutable) контейнер данных без бизнес-логики.

final class RegisterUserDto
{
    public function __construct(
        public readonly string $name,
        public readonly string $email,
        public readonly string $password,
    ) {}

    // Фабричный метод — создаёт DTO из HTTP-запроса
    public static function fromRequest(RegisterRequest $request): self
    {
        return new self(
            name:     $request->validated('name'),
            email:    $request->validated('email'),
            password: $request->validated('password'),
        );
    }

    // Можно создавать и из массива (например, для тестов)
    public static function fromArray(array $data): self
    {
        return new self(
            name:     $data['name'],
            email:    $data['email'],
            password: $data['password'],
        );
    }
}

Преимущества перед массивом:

  • Автодополнение в IDE (свойства известны на этапе написания кода).
  • Типобезопасность — невозможно передать ['namee' => ...] (опечатка) без ошибки.
  • Явный контракт между слоями.

4. Factory Pattern​

Цель: инкапсулировать логику создания объектов.

Simple Factory​

class NotificationFactory
{
    public static function create(string $channel, array $config): NotificationInterface
    {
        return match ($channel) {
            'email'    => new EmailNotification($config['smtp']),
            'telegram' => new TelegramNotification($config['bot_token']),
            'sms'      => new SmsNotification($config['api_key']),
            default    => throw new \InvalidArgumentException("Unknown channel: $channel"),
        };
    }
}

$notification = NotificationFactory::create('email', config('mail'));
$notification->send($user, 'Добро пожаловать!');

Laravel Model Factories (для тестов)​

// database/factories/UserFactory.php
class UserFactory extends Factory
{
    public function definition(): array
    {
        return [
            'name'       => $this->faker->name(),
            'email'      => $this->faker->unique()->safeEmail(),
            'password'   => bcrypt('password'),
            'is_active'  => true,
        ];
    }

    // Именованные состояния
    public function inactive(): static
    {
        return $this->state(['is_active' => false]);
    }

    public function admin(): static
    {
        return $this->state(['role' => 'admin']);
    }
}

// Использование в тестах
$user        = User::factory()->create();
$adminUser   = User::factory()->admin()->create();
$inactiveUser = User::factory()->inactive()->create();

// Создание нескольких
$users = User::factory()->count(5)->create();

5. Observer Pattern​

Цель: реагировать на события модели (создание, обновление, удаление) без загрязнения модели или сервиса этой логикой.

class UserObserver
{
    public function created(User $user): void
    {
        // Отправляем приветственное письмо при создании
        Mail::to($user->email)->send(new WelcomeEmail($user));
    }

    public function updated(User $user): void
    {
        // Инвалидируем кэш при изменении пользователя
        Cache::forget("user:{$user->id}");
    }

    public function deleted(User $user): void
    {
        // Логируем удаление
        Log::info("User deleted", ['id' => $user->id, 'email' => $user->email]);
    }
}

// Регистрация в AppServiceProvider или EventServiceProvider
User::observe(UserObserver::class);

6. Decorator Pattern​

Цель: добавить поведение к объекту без изменения его класса.

interface UserRepositoryInterface
{
    public function findById(int $id): ?User;
}

// Базовая реализация
class EloquentUserRepository implements UserRepositoryInterface
{
    public function findById(int $id): ?User
    {
        return User::find($id);
    }
}

// Декоратор с кэшированием
class CachedUserRepository implements UserRepositoryInterface
{
    public function __construct(
        private UserRepositoryInterface $inner,
        private Cache $cache,
        private int $ttl = 3600,
    ) {}

    public function findById(int $id): ?User
    {
        return $this->cache->remember(
            "user:$id",
            $this->ttl,
            fn() => $this->inner->findById($id)
        );
    }
}

// Биндинг с декоратором
$this->app->bind(UserRepositoryInterface::class, function ($app) {
    return new CachedUserRepository(
        new EloquentUserRepository(),
        $app->make(Cache::class),
    );
});
