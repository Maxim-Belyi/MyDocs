# Архитектуры приложений

Архитектура — это способ организации кода так, чтобы с ним было удобно работать, когда проект вырастает из «простого сайтика» во что-то гигантское.

> Ключевой принцип: **нет универсально «лучшей» архитектуры**. Есть правильный выбор под конкретный масштаб задачи.

---

## 1. MVC — Стандартный монолит (из коробки Laravel)

**MVC (Model-View-Controller)** — это базовый архитектурный паттерн, который Laravel предлагает вам из коробки. Код здесь сгруппирован по **техническому назначению**:

| Папка | Что лежит |
| :--- | :--- |
| `app/Http/Controllers` | Все контроллеры |
| `app/Models` | Все модели (таблицы БД) |
| `resources/views` | Все шаблоны (HTML) |

```
routes/web.php → Controller → Model → View → Ответ браузеру
```

**Плюсы:**
- Идеально для старта. Очень высокая скорость разработки.
- Понятно любому новичку с первого взгляда.
- Laravel, Symfony, Rails — всё так устроено.

**Минусы:**
- Когда проект становится огромным, папка `Controllers` разрастается до 200-500 файлов.
- Появляются «толстые контроллеры» (где 1000 строк логики) или «толстые модели».
- Начинается путаница: где хранить логику скидок — в контроллере заказов или в модели?

**Когда выбирать:** Стартап, MVP, небольшой корпоративный сайт, интернет-магазин среднего размера.

---

## 2. DDD — Предметно-ориентированное проектирование

**DDD (Domain-Driven Design)** — это не столько строгая структура папок, сколько **философия**. DDD говорит: «Хватит группировать файлы по типу (модели/контроллеры). Давайте группировать их по **бизнес-смыслу (Домену)**».

### Как меняется структура

```
// MVC: группируем по технической роли
app/
  Models/
    User.php
    Order.php
    Invoice.php
  Controllers/
    UserController.php
    OrderController.php
    InvoiceController.php

// DDD: группируем по бизнес-домену
src/
  Domain/
    Users/
      User.php
      UserRepository.php
      UserService.php
    Orders/
      Order.php
      OrderRepository.php
      OrderService.php
    Invoices/
      Invoice.php
      InvoiceService.php
      DispatchInvoiceCommand.php  // Бизнес-термин!
```

### Единый язык (Ubiquitous Language)

Одна из главных идей DDD — код пишется **терминами бизнеса**. Если бухгалтеры говорят «Провести накладную», то в коде метод должен называться `dispatchInvoice()`, а не `updateStatusToTrue()`. Программисты и бизнес говорят на одном языке.

**Плюсы:**
- Идеально для гигантских, сложных корпоративных систем (банки, ERP, логистика).
- Легко поддерживать разными командами: одна команда пишет только `Orders`, другая — `Invoices`.
- Легко выделять части в отдельные микросервисы.

**Минусы:**
- Очень высокий порог входа. Нужно хорошо знать теорию.
- Огромное количество boilerplate-кода (лишней писанины).
- Для 90% проектов — жуткий оверинжиниринг.

**Когда выбирать:** Банки, крупные финтех-компании, ERP-системы, проекты со сложной бизнес-логикой и командами 10+ человек.

## 3. Чистая архитектура (Clean / Hexagonal / Onion)

У этих трёх подходов разные названия, но суть одна: **бизнес-логика — это самое ценное, она должна быть в центре и ни от чего не зависеть.**

### Основная идея

Представьте луковицу (Onion Architecture). В центре — ваш чистый PHP-код бизнес-логики. Он вообще не знает, что такое Laravel, что такое HTTP, и какая база данных используется.

```
[ База данных (MySQL / MongoDB) ]
      [ Laravel / Eloquent ]        ← Адаптер (инфраструктура)
         [ Интерфейсы/Порты ]       ← "Розетки" для внешнего мира
            [ Бизнес-логика ]       ← Ядро, ничего не знает о внешнем мире
```

Всё общение с внешним миром происходит через «Порты» (Интерфейсы). Например, центральная логика говорит: «Мне нужен `UserRepositoryInterface`». А снаружи лежит «Адаптер» (написанный на Laravel Eloquent), который реализует этот интерфейс.

**Плюсы:**
- Можно выкинуть Laravel, выкинуть MySQL, переписать интерфейс с веба на консоль — и вам **не придется менять ни одной строчки в бизнес-логике**.
- Идеально тестируется: бизнес-логику можно тестировать без базы данных и HTTP-запросов.

**Минусы:**
- Требует очень высокой квалификации.
- Пишется медленно, много кода.

**Когда выбирать:** Проекты с критически важной бизнес-логикой и долгим жизненным циклом (10+ лет).

---

## 4. Микросервисы (Microservices)

Это когда мы берем наш монолит и физически **разрезаем** его на несколько отдельных маленьких приложений, которые работают на разных серверах и общаются друг с другом по сети (через API или очереди сообщений вроде RabbitMQ / Kafka).

```
Монолит:                   Микросервисы:
┌─────────────────┐         ┌───────────┐  ┌───────────┐
│  Авторизация    │         │ Auth      │  │ Catalog   │
│  Каталог        │  →→→    │ Service   │  │ Service   │
│  Корзина        │         └───────────┘  └───────────┘
│  Email-рассылка │         ┌───────────┐  ┌───────────┐
└─────────────────┘         │ Cart      │  │ Mailer    │
                            │ Service   │  │ Service   │
                            └───────────┘  └───────────┘
```

**Плюсы:**
- Каждый сервис можно писать на разных языках (Auth на PHP, Catalog на Go).
- Если падает сервис Email-рассылки — интернет-магазин всё равно принимает заказы.
- Легко масштабировать под высокими нагрузками: хотите — поднимите 10 копий только сервиса каталога.

**Минусы:**
- Инфраструктурный ад: нужны Kubernetes, Docker, service mesh.
- Сложно дебажить («Запрос потерялся где-то между 4-м и 5-м микросервисом»).
- Сложно обеспечить целостность данных (транзакция сразу в трёх базах данных).
- Подходит только для зрелых команд с сильными DevOps-практиками.

**Когда выбирать:** Высоконагруженные проекты (Amazon, Netflix, Spotify), команды 50+ разработчиков.

---

## Как сравнить всё на одной схеме

| | MVC Монолит | DDD | Чистая Архитектура | Микросервисы |
| :--- | :--- | :--- | :--- | :--- |
| **Сложность** | Низкая | Высокая | Очень высокая | Очень высокая |
| **Скорость разработки** | Быстро | Медленно | Медленно | Очень медленно |
| **Масштабируемость** | Ограничена | Хорошая | Хорошая | Отличная |
| **Для команды** | 1-5 чел. | 5-20 чел. | 5-20 чел. | 50+ чел. |
| **Тестируемость** | Средняя | Хорошая | Отличная | Сложная |

---

### Резюме для собеседования

«Выбор архитектуры зависит от масштаба задачи:
- Для **стартапа** или MVP — **MVC-монолит Laravel**: быстро, просто, всё под рукой.
- Для **сложной корпоративной системы** с запутанной бизнес-логикой — элементы **DDD и Чистой архитектуры**: бизнес-логика в центре, не зависит от фреймворка.
- **Микросервисы** — только тогда, когда монолит уже упирается в пределы производительности или над проектом работают сотни разработчиков. Начинать с микросервисов — это классическая ошибка.»
